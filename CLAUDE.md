## Project Overview

A meal planning and fridge inventory manager structured as a Hermes plugin. The entry point is `__init__.py:register(ctx)`, which auto-discovers the twenty-six tool handlers under `src/handlers/` and installs the skill. All state is persisted in JSON files under `data/`.

Python 3.12+, no external **runtime** dependencies (stdlib only). `mypy`, `ruff` and `coverage` are development/CI-only tools, pinned in CI and configured in `pyproject.toml` — nothing under `src/` or `__init__.py` imports them, and no runtime code depends on them.

## Architecture

### Plugin wiring layer (top-level files)

- **`__init__.py`** — `register(ctx, *, data_dir=None)` walks `src/handlers/` via `iter_tools()` and registers each `(NAME, SCHEMA, HANDLER)` triple, then injects `skill.md` into the Hermes context. There is no central handler list to maintain — adding a new tool is a matter of dropping a new module into `src/handlers/`. If the host supplies a `data_dir`, `register` calls `src.repositories.configure(data_dir)` and `src.dii.configure(data_dir / "sessions")` so all persistence is redirected to that location.
- **`plugin.yaml`** — Declares the plugin name (`meal_manager`), its `version`, and lists provided tools (kept manually in sync with the modules under `src/handlers/`). `version` is a documented Hermes manifest field but nothing validates or consumes it, so it is declarative only — bump it in the same commit as the release tag or the two drift silently.
- **`skill.md`** — LLM-facing instructions for when/how to invoke each tool. The DII section instructs the agent to drive ingredient selection via plain text conversation, interpreting free-text user responses to call the appropriate DII tool.

### Handlers (`src/handlers/`)

One module per registered tool. Each public submodule (anything not prefixed with `_`) exports three module-level attributes:

- `NAME: str` — tool name passed to `ctx.register_tool`.
- `SCHEMA: dict` — JSON schema with a top-level `description`.
- `HANDLER: Callable[[dict, ...], str]` — handler function. Decorated with `@tool_handler(NAME, SCHEMA)` from `_common.py`, the body returns a plain Python object (dict, list, str, …) and raises on validation/business errors. The decorator centralizes JSON serialization (`json.dumps(..., ensure_ascii=False)`) and error handling: any exception is logged via `logger.exception` and surfaced through the sanitized unified `{"error": ...}` envelope.

`src/handlers/__init__.py:iter_tools()` walks the package via `pkgutil.iter_modules`, importing each non-underscore module and yielding its `(NAME, SCHEMA, HANDLER)` triple in alphabetical order. Modules starting with `_` (like `_common.py`) are skipped.

- **`_common.py`** — Shared helpers: `tool_handler` decorator (the canonical wrapper for every handler), `reject_unknown_args` (the schema-derived argument check the decorator applies), `_safe_error_message` (maps an exception to the text allowed to leave the process), `require_arg` (explicit "required argument" error instead of a bare `KeyError`), `maybe_parse_json_arg` (coerces JSON-string arguments that some LLMs emit), `normalize_dish_name`, `normalize_ingredient_name` (which also resolves ingredient aliases — see below), `normalize_ingredients`, `normalize_ingredient_entries` (the fridge-side mirror of `normalize_ingredients`: accepts `["a", "b"]`, `{"a": 3, "salt": null}`, or `{"milk": {"count": 2, "expires_on": "2026-08-01"}}` and yields `{name: spec}`), `normalize_ingredient_names` (names only, for paths like fridge removal where a count is meaningless and must not be validated), `days_since_last_cook`, plus the input-limit constants (`MAX_NAME_LEN`, `MAX_INGREDIENTS`, `MAX_BATCH_SIZE`, `MAX_FRIDGE_UPDATE`, `MAX_PORTION_COUNT`). Both `normalize_dish_name` and `normalize_ingredient_name` delegate to a single `_normalize_label(value, *, label)` helper so the rules (non-empty, max length) live in one place.

  `normalize_ingredient_entries` returns a spec that always carries `"count"` but carries `"expires_on"` only when the caller supplied it, so a handler can distinguish "clear the date" (explicit `null`) from "leave the date alone" (key absent).

  **Unknown arguments are rejected.** `tool_handler(NAME, SCHEMA)` computes the allowed key set from `SCHEMA["properties"]` once at decoration time and validates `args` inside the try block, so a rejected key comes back through the normal error envelope. Deriving the set from the schema means the check cannot drift from the declared interface. `tool_handler(NAME)` without a schema stays unvalidated.

  **The error envelope is sanitized.** `ValueError` and `LookupError` (including `KeyError`) are raised deliberately by handlers with user-facing wording, so their message passes through verbatim. `OSError` becomes "Storage is temporarily unavailable" and `json.JSONDecodeError` becomes "Stored data could not be read" — they carry absolute paths and byte offsets into file contents. Anything else becomes "An internal error occurred", because an unanticipated exception type is exactly where `str(exc)` is most likely to publish something unintended. `JSONDecodeError` subclasses `ValueError`, so it is tested first. Full detail always still reaches `logger.exception`.

### Domain modules (`src/`)

- **`dish.py`** — Module-level `clean_label(value, *, label)` (strip, lowercase, reject non-strings) plus the `Dish` dataclass. `clean_label` is public and sits outside the class because the rule belongs to neither layer: `Dish.normalize_name` / `Dish.normalize_ingredient` and `handlers/_common._normalize_label` (which layers the non-empty check and length cap on top) both call it. It was `Dish._clean` until `_common` reaching into it became the only place one layer touched another's private API. `Dish` is the recipe model with `ingredients` dict mapping name → `bool` (True = essential, False = optional). `__post_init__` enforces the invariant that `Dish.name` is always stored stripped and lowercased — every construction path (direct, `from_dict`, dataclass `replace`) goes through it, so consumers can compare `dish.name` by equality without re-normalizing. It applies the same checks to `ingredients` that `add_ingredient` does (non-empty name, boolean flag), so direct construction cannot smuggle in a nameless ingredient or a truthy non-bool that `can_cook_with` would read as essential. Code that assigns `dish.ingredients` wholesale (`edit_dish`, the DII finalizer) bypasses `__post_init__` and is responsible for passing an already-validated map — both feed it one. `can_cook_with()` checks if all essential ingredients are available. `instructions` is optional free-form cooking text, capped at `MAX_INSTRUCTIONS_LENGTH` (20,000 chars) and validated by `normalize_instructions`: blank collapses to `None`, because "cleared" and "never set" are one state and two representations of it would have to be handled everywhere downstream. Serialization uses English keys (`name`, `ingredients`, and `instructions` **only when set** — so a catalog with no instructions round-trips byte-identically). Legacy data files may contain `prep_time` which is silently ignored on load.
- **`suggestion.py`** — Scoring engine. `score_components()` returns the weight-independent `(match, recency)` pair (or `None` when a dish is gated out by the cooldown or has no ingredients); `calculate_score()` blends that ingredient-match term with that recency term using the supplied weights. Splitting the two lets the tuning learner rank one catalog under nine candidate weights while walking each dish's ingredients only once. Essentials are **not** part of the score: they are a gate, already enforced by `can_cook_with` (and by the shopping simulation), so scoring them again would only add a constant. The match term is the number of *optional* ingredients actually in stock, capped at `OPTIONAL_CAP` (3) and normalized — an absolute count, not an intra-dish ratio, so declaring an optional you have raises the score and declaring one you lack is free. Recency is normalized over 14 days. Dishes cooked < 2 days ago score 0. The blend weight between the two terms is the learner's deployed `w` (`match_weight`/`time_weight`), defaulting to 0.6/0.4. `suggest_dishes()` filters to cookable dishes and ranks by score.
- **`shopping.py`** — `suggest_quick_shopping()` finds dishes missing at most `max_missing` essential ingredients (default 1), simulates having all of them, scores the result, and credits every missing essential of the near-miss dish. Returns `(ingredient, dish_names, score, unlocks_count, still_missing)` tuples sorted by **cheapest basket first** (`still_missing` ascending), then reach (`unlocks_count` descending), then score, then ingredient name for deterministic ties. `still_missing` is the smallest basket size that unlocks a dish through that ingredient, and **every other field on the row describes that same basket**: `dish_names`/`unlocks_count` cover only the dishes it actually reaches and `score` is the best of those, so a row never advertises a meal its own basket cannot buy. Letting the dish set span every basket size while the score tracked only the cheapest produced rows reading "buy this one thing, unlocks 3 dishes" when one purchase unlocked one; a dish reachable only from a pricier basket still surfaces through the other ingredients that basket needs, at its true size.
- **`tuning.py`** — Online self-tuning of the availability/recency blend. Pure functions only (no I/O, no locking, no randomness): `initialize_state`/`validate_state` manage the `data/tuning.json` shape (non-finite `S`/`C` mass is treated as corruption — NaN passes an `isinstance` check but makes every hysteresis comparison `False`, silently freezing the weight forever; the `candidates` list is validated entry by entry rather than by set comparison, because filtering non-numeric entries out of that check let a polluted list validate and then raise `TypeError` inside `select_deployed`, which the cook handler swallows — the same silent permanent freeze by another route); `compute_rewards` replays a cook decision against the pre-cook snapshot and rewards every availability-weight candidate `w` by how highly it ranked the cooked dish (via `score_components`, computed once per dish and re-blended per candidate), returning `None` for events that carry no signal about `w` (fewer than two *rankable* dishes, the dish was dropped from every ranking, or the reward vector is uniform within `MIN_REWARD_SPREAD` — applying any of these would only discount accumulated mass by `GAMMA`). The reward is a rank normalized over the size of the ranking the dish actually appeared in, not over every cookable dish: dishes gated out by the cooldown never enter any candidate's ranking, so counting them stretched the scale and pushed rewards toward 1.0 whenever the catalog was mostly cooling down; `apply_update` applies the discounted (`GAMMA`) reward/count update; `select_deployed` picks the deployed `w` (cold-start anchor below `MIN_OBSERVATIONS`, then argmax-within-`BAND` gated by `HYSTERESIS_MARGIN`) and compares the challenger against the **nearest in-band candidate** to the stored weight rather than the stored weight itself: `BAND`'s lower bound (0.35) sits below the candidate grid (0.40+), so a clamped weight can carry no accumulated mass, and reading its absent mass as a 0.0 mean let any candidate clear the margin against nothing. Snapping to the nearest candidate also walks an off-grid weight back onto the grid, and is the identity for a weight already on it. `deployed_weights` is the safe reader. Hyperparameters are module constants. `suggest_dishes` accepts `match_weight`/`time_weight`, so the deployed blend feeds straight in.

- **`history_event.py`** — `CookingEvent` dataclass: one recorded cook (`id`, `dish_name`, `cooked_on`, `recorded_at`, `backfilled`, `retracted_at`). Pure data, no I/O. `__post_init__` validates every field (tz-aware datetimes, canonical ISO dates, a `cook_` id prefix); `from_dict` is strict about unknown *and* missing keys, because it reads data we wrote ourselves and an unrecognized shape is corruption to surface rather than absorb. `dish_name` is a snapshot at cook time — renaming a dish in the catalog does not rewrite history. The fork's `time_precision`, `plan_occurrence_id`, `actual_portions`, `actual_yield_portions` and `provenance` fields are deliberately absent: they serve the weekly-plan feature, which is out of scope.

### Persistence layer (`src/repositories/`)

All file-backed state lives behind repository singletons defined in `src/repositories/__init__.py` (`dish_repo`, `fridge_repo`, `history_repo`, `tuning_repo`, `alias_repo`). Consumers depend on the `Protocol` types in `base.py`, not on the concrete `Json*Repository` classes — this is the seam that lets tests swap implementations without monkey-patching module-level functions.

The data directory is injectable via `src.repositories.configure(data_dir)` — this mutates the existing singletons' `path` attributes in place so modules that already imported `dish_repo` / `fridge_repo` / `history_repo` / `tuning_repo` / `alias_repo` keep a valid reference. The default (when `configure` is never called) is `<plugin_root>/data/`. `configure` also moves the lock file, so a test run on a `mkdtemp()` path never contends with the real `data/`.

**Locking is cross-process.** `src/filelock.py` defines `DataDirLock` and the shared `data_lock` singleton: one advisory `fcntl.flock` over `<data_dir>/.lock` covering the whole data directory. All five repositories assign that one object to the same `self.lock` / `self._lock` attribute they already had, which is why every existing `with dish_repo.lock:` call site — in the repositories and in the handlers — needed no edit. It is **reentrant**: repository methods nest (`save` calls `load_entries`) and handlers hold one repository's lock while calling into another, so a non-reentrant shared lock would deadlock on the first nested call. The lock file is opened per critical section and closed on release, since a long-lived fd would go stale across `configure()`. Where `fcntl` is unavailable (Windows) it degrades to an in-process lock, matching the best-effort posture of `atomic_write_json`'s directory fsync. Acquisition is a polled `LOCK_NB` bounded by `LOCK_TIMEOUT_SECONDS` (30) rather than a blocking `LOCK_EX`: an unbounded wait let one wedged holder freeze every tool with nothing to report. On expiry it raises `DataLockTimeout` (a `TimeoutError`, so generic I/O handling still catches it), which `_safe_error_message` surfaces verbatim ahead of the generic `OSError` branch.

- **`base.py`** — `DishRepository`, `FridgeRepository`, `HistoryRepository`, `AliasRepository`, `TuningRepository` Protocols. `path: Path` is a plain attribute because `configure()` reassigns it in place; `lock` is a **read-only property** returning an `AbstractContextManager`, because a mutable protocol attribute is invariant and would admit only something that is exactly an `AbstractContextManager` — rejecting the shared `DataDirLock`. Nothing reassigns `.lock`.
- **`json_dish.py`** — `JsonDishRepository` (`<data_dir>/dishes.json`, wraps the `{"dishes": [...]}` envelope). Takes the shared `data_lock` for load-modify-save sequences. `restore(dish)` is the delta-rollback for delete. `_parse()` splits the file into parsed dishes and the raw rows that failed in a single pass; `load()` caches the failures on the instance so `save()` can round-trip them without a second read-and-reparse of the whole catalog. Every caller does load-modify-save under `lock`, so the cache is still accurate at save time; `save()` falls back to a fresh parse if the instance has never loaded.
- **`json_fridge.py`** — `JsonFridgeRepository` (`<data_dir>/fridge.json`, a `{name: value}` object, lowercased on load). A value is either a bare count or an object carrying an expiry: `{"milk": {"count": 2, "expires_on": "2026-08-01"}}`. The object form is purely additive — scalars and `null` keep their exact meaning, and entries without a date are still written as bare scalars, so an existing file round-trips with no diff. `load()`/`save()` keep the count-only `{name: count}` view every existing caller consumes; `load_entries()`/`save_entries()` are the richer pair that sees the dates. `save()`, `consume()` and `remove_items()` all round-trip the count-only view, so they merge stored dates back in rather than erasing them, and all three hold the lock across the load-modify-save window — `save()` previously ran its `load_entries()` + `save_entries()` pair with no lock at all. `expiry_status(expires_on, today)` classifies a date as `expired` / `expiring_soon` (within `EXPIRING_SOON_DAYS`, 3) / `fresh`, or `None` when there is no date. An unreadable date on disk costs the date, not the ingredient. `load_entries()` swallows `OSError` alongside the parse errors, so an unreadable `fridge.json` degrades to an empty inventory like every other data file rather than being the one file in the set that hard-fails into an error envelope. For counts: `None` = pantry staple (unlimited, never decremented), `0` = known to be out of stock, `n > 0` = approximately `n` dish-portions. Non-finite counts are dropped with a warning: Python's `json` accepts the non-standard `NaN`/`Infinity` literals, and both raise out of `int()` *outside* the parse guard (`ValueError` and `OverflowError` respectively), which turned one hand-edited value into an error envelope from every fridge-backed tool. Legacy flat-list files are migrated in memory on load (each name becomes one portion) and written back in the new shape on the next save, so no migration step is needed. `load_set()` returns only the *usable* names — this is the seam that keeps the scoring core unaware of counts. `remove_items(items)` is the delta-rollback used by the DII finalizer. `consume(names)` decrements one portion per essential for the cook handler and returns `{name: previous_count}` so the caller can report what moved; it has no rollback counterpart because the whole decrement lands in one locked load-modify-save, leaving no half-applied state to compensate for.
- **`json_alias.py`** — `JsonAliasRepository` (`<data_dir>/aliases.json`, a flat `{alias: canonical}` map). Missing/corrupt files load as `{}`. `resolve(name)` is a **single hop, never a loop** — `add()` earns that by re-pointing any alias that targeted the name being retired, so a chain can never form, and a loop here would hang on a hand-edited file containing a cycle. Reads are lock-free like the other repositories; `add()` takes `self.lock`. Reads are also **cached**, keyed on a `(path, inode, mtime_ns, size)` stat fingerprint: `resolve()` runs once per ingredient name at the tool boundary, so re-parsing the file each time made a single 100-ingredient `add_dish` do 100 opens. `atomic_write_json` replaces the file rather than rewriting it, so the inode always changes; `save()` also drops the cache outright. `load()` returns a copy because the cached mapping is shared and `add()` mutates what it receives.
- **`json_history.py`** — `JsonHistoryRepository` (`<data_dir>/history.json`, `{"schema_version": 2, "events": [...]}`) — an append-only log of `CookingEvent`. `load()` keeps the historical `{dish name: ISO date}` contract by *projecting* the log: the latest `cooked_on` per dish, retracted events excluded. Because the projection takes a maximum, an older event can never displace a newer one. `load_events(strict=False)` returns the raw log and migrates a legacy `{dish: date}` file in memory (ids via `uuid5` so re-migrating is idempotent); it never writes, and the v2 shape lands on the next mutating call. With `strict=True` corrupt storage raises `HistoryDataError` instead of yielding an empty log. "Corrupt" includes an unreadable file: `OSError` is wrapped in `HistoryDataError` too, so the non-strict contract holds for I/O errors as well — otherwise a permissions glitch on `history.json` took down `get_meal_suggestions` entirely while the same glitch on `dishes.json` or `fridge.json` degraded quietly. `append_event`, `retract_event`, `retract_latest_for_dish` and `retract_all_for_dish` are the write paths; `delete_event` is the hard delete reserved for rollback. Holds the shared `data_lock` itself, so callers never acquire it.
- **`json_tuning.py`** — `JsonTuningRepository` (`<data_dir>/tuning.json`, the online-learner state). Exposes the shared `data_lock` for the cook handler's load-modify-save sequence. `load()` never raises: a missing/corrupt/schema-invalid file yields a fresh `tuning.initialize_state()`.

### DII (`src/dii/`)

- **`session.py`** — `DIISession` dataclass plus ISO-time helpers and `to_dict`/`from_dict` serialization. Pure data; no I/O. `from_dict` **validates** rather than trusting what it reads: a restored backup is hand-editable and older-format files exist, so it type-checks the flags, requires a non-empty `ingredient` on every queue entry (the engine indexes that key directly, and a missing one surfaced as `{"error": "'ingredient'"}`), and resolves a name present in *both* selected lists the way `merge_ingredient_alias` does — essential wins, because the finalizer's map union used to silently demote it to optional. Raising is the intended outcome for a shape that cannot be trusted: `store.py` catches it and unlinks the backup as corrupt.
- **`store.py`** — `IngredientSessionStore`: in-memory session map mirrored to `data/sessions/` for crash recovery, with TTL cleanup (30 min) debounced by monotonic clock. Owns the global lock and the per-session lock map. Per-session locks are handed out only by the `session_lock(session_id)` context manager, which reference-counts holders and deletes the entry when the last one leaves — nothing else may prune the map. Deleting a lock does not release it, so evicting one mid-critical-section (as the old TTL and orphan-sweep paths did) hands the next caller a fresh mutex and lets two writers into the same session. The orphan sweep treats a backup holding **valid JSON of the wrong shape** (an array, say) as corruption and unlinks it: reading `last_activity` off a non-dict raised `AttributeError` out of the sweep, which escaped `cleanup_expired()` and then `get()`, so one stray file turned every DII tool into an error envelope — including the sweep that would have removed it.
- **`engine.py`** — Pure mutations on a `DIISession` (build, add/skip/remove/add_manual/clear/mark_finalized). No I/O, no locking — those concerns live in the store and the public API. The "essential XOR optional" rule is enforced in a single `_select(session, name, *, essential)` helper used by every code path that adds an ingredient to a selected list. `build_session` is the orchestrator: validation, normalization, session construction, pre-selection, and queue seeding each live in their own named helper.
- **`presenter.py`** — Builds the LLM-facing response shape (`next_actions`, `instructions`). Decoupled from the engine so the agent UX can change without touching state logic.
- **`finalizer.py`** — Commits a session via injected `dish_repo` + `fridge_repo`, with delta-rollback of the fridge (`fridge_repo.remove_items`) if the dish save fails. Where a name appears in both selected lists — impossible via the engine, possible via a restored backup — **essential wins**, matching `merge_ingredient_alias`; a dict union resolved it as optional and silently demoted the essential. Returns `(committed_fridge, committed_dish, items_added_to_fridge)`: `committed_fridge` reports that the commit *ran*, not that it changed anything — a session whose ingredients were all already stocked is as committed as one that added three, and reporting `False` there reads as a failure. The count carries the "how much actually changed" signal, surfaced to the agent as `fridge_items_added`.
- **`__init__.py`** — Public API: composes the store, engine, presenter, and finalizer into the eight functions consumed by the DII handler modules. Holds the default `IngredientSessionStore` singleton. Also exposes `configure(session_dir)` so hosts and tests can redirect the on-disk session backup directory in place.

### Data files (`data/`)

- `dishes.json` — Recipe catalog. Wraps dishes in `{"dishes": [...]}`; each dish has `name`, `ingredients` (name → bool), and optionally `instructions` (free-form text, emitted only when set).
- `fridge.json` — Fridge inventory: an object mapping ingredient name → either a portion count (`null` = pantry staple, `0` = known out of stock) or an object `{"count": n, "expires_on": "YYYY-MM-DD"}` when an expiry is known. Entries without an expiry stay bare scalars. Legacy flat-array files are migrated automatically on first load.
- `history.json` — Cooking history: `{"schema_version": 2, "events": [...]}`, an append-only log of cook events. Legacy `{dish: date}` files are migrated in memory on load and rewritten in the v2 shape on the next write.
- `aliases.json` — (created lazily on the first merge) Ingredient aliases: a flat `{alias: canonical}` map consulted at the tool boundary.
- `tuning.json` — (created lazily on the first learning event) Online-learner state for the suggestion blend: candidate grid, discounted reward/count sums (`S`/`C`), `observations`, and the `deployed_match_weight` / `deployed_time_weight`. Missing/corrupt files fall back to a fresh initialized state.
- `sessions/` — (created lazily) Per-session DII JSON backups for crash recovery. Files are named `{session_id}.json` and auto-cleaned after 30 minutes.
- `.lock` — (created lazily on the first locked operation) The advisory cross-process lock file for the whole data directory. Empty; only its `flock` state matters. Never read or written as data, and moved by `configure()` along with everything else.
- `.mm-tmp-*.tmp` — (transient) Temp files from `atomic_write_json`. A write killed before its `os.replace` leaves one behind, so the next successful write in that directory sweeps any older than an hour — nothing else scans `data/`. `atomic_write_json` also copies the target's permissions onto the temp file, since `mkstemp` creates 0600 and `os.replace` would otherwise narrow every data file on its first write through it.

## Key Design Decisions

- **One lock for the data directory, not one per file**: Every repository used to serialize with its own `threading.Lock`, which binds a single process. `atomic_write_json` guarantees no torn file, but two processes running load-modify-save against the same JSON silently lose one update — the write is clobbered, not corrupted. The fix is a single advisory `flock` over the whole data directory (`src/filelock.py`). Per-file locks were rejected: five of them would force a global acquisition order, and handlers touching several (`register_cooked_meal` touches four) would become a deadlock source. Because all five repositories share the one object, cross-repository atomicity is available for free — but only to handlers that actually nest it. Acquiring and releasing per repository still yields independent windows, so the three multi-repository mutating handlers (`register_cooked_meal`, `merge_ingredient_alias`, `delete_dish`) open one explicit `with data_lock:` around their whole sequence. Their hand-rolled compensation is still needed for in-window failures, but nothing can now observe the half-applied state between the steps. The accepted cost is stated plainly: every data operation serializes process-wide. That is irrelevant for a single-user personal tool, and it is why the lock can be this coarse.
- **Essential vs optional ingredients**: In `Dish.ingredients`, `True` = essential (must have to cook), `False` = optional (improves score but not required).
- **Unknown tool arguments are rejected, not ignored**: silently dropping an unrecognized key meant a caller that passed `dish_name` instead of `name` got a confusing error about the *missing* key — or worse, the handler ran with defaults nobody asked for. The allowed set is derived from each handler's own `SCHEMA["properties"]` so it cannot drift from the declared interface.
- **The error envelope is sanitized**: deliberate `ValueError`/`LookupError` messages pass through verbatim because handlers write them for the user; `OSError` and `JSONDecodeError` are replaced because they carry filesystem paths and file contents, and everything else gets a generic message because an unanticipated exception type is exactly where leaking is most likely. See `_common.py` above.
- **Aliases merge once, then canonicalize at the boundary**: `"tomate"`, `"tomates"` and `"tomate pera"` were three distinct keys, so the fridge accumulated near-duplicates and `can_cook_with` failed against a dish that spelled an ingredient differently. `merge_ingredient_alias` rewrites the catalog and fridge once and records the alias; `_common.normalize_ingredient_name` consults it thereafter. Deliberately *not* a read-time projection — rewriting once is cheaper than resolving forever and leaves the stored data honest. `Dish.normalize_ingredient` stays pure and I/O-free: only the tool boundary resolves aliases. That makes it the *whole* tool boundary's job — including the DII handlers. `init_ingredient_session` must build the session from canonical names and `dii_remove_ingredient` must resolve before looking one up, or a session seeded with a retired spelling commits it straight back into the catalog and fridge, and an ingredient added under its canonical name can never be removed by the name the user typed.
- **Essential wins on an alias merge**: where a recipe lists both spellings, the merged flag is `essential[from] or essential[to]`. Demoting an essential to optional would let `can_cook_with` approve a dish the user cannot actually make. In the fridge, counts sum (clamped to `MAX_PORTION_COUNT`) and a staple beats any number.
- **Expired food stays available**: `expiry_status` flags an item as expired but nothing removes it, and `load_set()` still returns it. The date is the user's estimate, not ground truth, and silently deleting someone's food is not a call this tool gets to make — flag it and let them decide.
- **Adaptive suggestion weights**: The availability/recency blend is no longer a fixed source constant — a bounded online learner (`src/tuning.py`, state in `data/tuning.json`) nudges the availability weight `w` (recency is always `1 - w`) one step per cooked meal, full-information and event-driven (no daemon, no randomness). This softens the deterministic-core promise **by design and with maintainer approval**: output stays deterministic *given* `tuning.json`, the weight is bounded to `BAND`, slow-moving (discounted, hysteresis-gated, cold-start-anchored), and auditable via the read-only `get_tuning_state` tool. A fresh/missing `tuning.json` reproduces the historical 0.6/0.4 blend until `MIN_OBSERVATIONS` cooks accumulate.
- **Essentials gate, optionals score**: `calculate_score` never scores essentials. Both production callers guarantee complete essentials before calling (`suggest_dishes` pre-filters with `can_cook_with`; `suggest_quick_shopping` simulates the missing ones), so an essential term would be a constant `1.0` with no discriminating power. The match signal is the capped *count* of optionals in stock. A count rather than a ratio is deliberate: under a ratio, declaring no optionals scored identically to having them all, so describing a recipe more carefully lowered its score — an inverted incentive that degraded the catalog over time.
- **Recency cooldown**: Dishes cooked fewer than 2 days ago are always excluded (score forced to 0).
- **Auto-removal on cook**: `register_cooked_meal` consumes one portion of each essential ingredient from the fridge after recording the meal. Pantry staples are untouched and counts floor at 0 rather than being deleted.
- **Portion counts, not quantities**: The fridge stores approximate dish-portions, and one cooked dish consumes one portion of each essential. This is deliberately approximate — real dishes use differing amounts — but it is strictly better than the previous all-or-nothing deletion, and it avoids forcing the user to enter grams. The `set` action on `update_fridge_inventory` exists so drift can be corrected cheaply; per-dish ingredient quantities are explicitly out of scope. `MAX_PORTION_COUNT` bounds the stored total, not just the argument — `add` clamps the running sum, so repeated restocking cannot walk past the ceiling. An `add` against a pantry staple stays a no-op on the count, but an `expires_on` sent with it is still recorded rather than dropped.
- **Pantry staples are unlimited**: A `null` count marks an ingredient that never runs out (salt, oil, spices). Staples always count as available and are never decremented by a cook, so the user is not asked to re-stock things they always have.
- **Backdated cooks skip learning**: `register_cooked_meal` accepts an optional `date`. The fridge is still consumed (the ingredients really were used, and the fridge reflects the present), but the tuning update is skipped — the learner replays the decision against a snapshot of *today's* fridge and history, which does not correspond to the backdated moment.
- **History is an append-only log, projected on read**: `history.json` used to store one date per dish, which made a plain write destructive when the incoming date was older than what was stored — logging a forgotten meal from last month reset a dish cooked this morning and handed it back to the suggestion engine. That needed an `only_if_newer` flag to paper over it. The log fixes it *by construction*: `load()` projects the maximum `cooked_on` per dish, so an older event simply cannot win, and the response tells the user their cooldown is unchanged. It also makes things possible that were not before — counting how often a dish was cooked, and taking an entry back without destroying it.
- **Retraction is not deletion**: `delete_history_entry` retracts the most recent cook — the row stays in the log and stays visible through `list_cooking_history`, it just stops counting toward the projection. `register_cooked_meal`'s rollback path uses `delete_event` instead, because a cook whose fridge consumption failed never happened and must leave no trace. `delete_dish` retracts every event for the dish it removes. Two different operations, deliberately not merged.
- **Near-miss unlock**: Shopping suggestions surface dishes at most `max_missing` essential ingredients away from cookable (default 1). Raising it is what makes the tool answer usefully on a near-empty fridge, where single-ingredient unlocks do not exist. Results rank by basket size first, then reach, then score. Reach alone was the wrong lead key once `max_missing > 1`: an ingredient named by three dishes that each need two more items unlocks nothing when bought alone, and outranked an ingredient that puts dinner on the table tonight. At the default `max_missing=1` every basket is size 1, so the ordering is unchanged there.
- **Colliding names are a contradiction, not a duplicate.** Two dict keys that normalize to the same ingredient can carry different flags or counts (`{"Rice": true, "rice": false}`), so `Dish.__post_init__`, `normalize_ingredients`, and `normalize_ingredient_entries` all raise rather than let one value silently win. List input still collapses repeats, because every list entry means the same thing. `Dish.from_dict` stays permissive on purpose: raising there would drop an existing catalog row from the catalog entirely instead of just flagging it.
- **Names are normalized once at the boundary; downstream code trusts the invariant.** Ingredient names go through `Dish.normalize_ingredient` / `_common.normalize_ingredient_name`; dish names go through `Dish.normalize_name` / `_common.normalize_dish_name`. `Dish.__post_init__` enforces that `Dish.name` is always stored normalized, so consumers compare `dish.name == name` directly — they do not re-`strip().lower()`.
- **JSON keys are in English** (`name`, `ingredients`, `dishes`) matching the Python code.
- **DII probability funnel**: Sessions hold a hidden queue of ranked ingredients. Only one suggestion is revealed at a time. The LLM provides the ranked list; the tool layer manages the reveal-one-at-a-time state.
- **DII user interaction via conversation**: The DII flow uses plain text conversation — the agent presents one suggestion at a time and interprets the user's free-text response (e.g. "yes", "skip", "add X") to call the appropriate DII tool. The DII tools are platform-agnostic; `skill.md` defines the conversational presentation strategy.
- **Recalculation signal**: When an essential ingredient is removed from a DII session, the tool returns `recalculation_needed: true`. The LLM decides whether to regenerate the ranked list — the tool layer never calls the LLM itself.
- **DII session lifecycle**: `init_ingredient_session` → manipulate via add/skip/remove/manual/clear tools → `finalize_ingredient_session` commits to fridge and/or dish catalog. Sessions are in-memory with optional JSON persistence under `data/sessions/`.
- **Relative imports throughout**: All internal imports use relative form (e.g. `from .src.repositories import dish_repo`, `from .dish import ...`) because Hermes loads the plugin as `hermes_plugins.meal_manager`. Absolute imports like `from src.xxx` would fail at runtime. The test files (`test_integration.py` and `test_unit.py`) bootstrap the package via `importlib` to make relative imports work when running standalone.
- **Injectable data directory**: `src/repositories/__init__.py:configure(data_dir)` and `src/dii/__init__.py:configure(session_dir)` mutate the singleton `path`/`session_dir` attributes in place. The top-level `register(ctx, *, data_dir=None)` wires both. `test_integration.py` uses this to point the whole plugin at a `tempfile.mkdtemp()` directory, so the real `data/` is never touched during tests and no backup/restore dance is needed.

## Git workflow

`main` is protected by a branch ruleset: **direct pushes are rejected**, and merging requires the `ci-complete` status check to pass. So the loop is: branch, push, open a PR, let CI go green, merge. Review approvals are **not** required (the count is 0), so a solo change is still a one-person operation — the gate is CI, not a second pair of eyes.

`ci-complete` (`.github/workflows/tests.yml`) is a single aggregating job that fails unless `tests`, `types`, `coverage`, `backend`, `frontend`, and `browser-e2e` all succeeded. **Any new job must be added to its `needs:` list**, or it silently stops gating anything. The ruleset requires that one stable name rather than the individual matrix legs on purpose: a dropped Python version would otherwise become a required check that never reports again and blocks every merge permanently.

GitHub Actions are pinned to **full commit SHAs** with a trailing `# vX.Y.Z` comment, never to tags — a tag can be repointed by its upstream owner, a commit SHA cannot. Keep new `uses:` lines pinned the same way.

This convention is shared across all six plugin repositories in this account.
