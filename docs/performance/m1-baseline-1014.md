五端点为认证后的库存、菜谱第一页、首页、推荐和做饭历史第一页。混合场景循环请求、50～100ms思考时间，预热5秒；测量通常45秒，允许请求排空，RPS分母包含排空尾部。原始CSV保留预热、完成时间、响应耗时及失败标记；P50/P95采用 nearest-rank，失败样本也计入。详见 [工具与重跑说明](README.md)、[完整指标CSV](results/m1-1014-01/baseline.csv) 与 [离线汇总](results/m1-1014-01/summary.json)。

## 执行计划、连接与资源

保存73个“规模/模板”组合的EXPLAIN JSON、EXPLAIN ANALYZE及profile：[sql-plans-and-profiles.json](results/m1-1014-01/sql-plans-and-profiles.json)。不是73种不同SQL。500规模库存用user_id索引读2000批次、过滤后1882、排序取100，实测约5.35ms；菜谱列表user_id索引500行后排序取100约0.822ms；单菜谱食材唯一索引取5行、Ingredient主键关联约0.042ms。历史排序约1～3ms。现有计划说明查询次数和Python重复计算比这些单条SQL更值得先处理。

100菜谱20个同时推荐的诊断中，18个200、2个503；失败请求没有SQL，池获取分别30000.3/30008.0ms、持有0。成功请求229SQL，耗时22.49～35.96秒；部分连接先被持有22～30秒，另3个成功请求等待22～29秒。与15连接上限/30秒等待一致。acquire还包含新建连接，不能称为纯排队时间。失败探针退出1，保留 [parallel-outcome.json](results/m1-1014-01/parallel-outcome.json)。原始API混合100/20没有HTTP失败，二者不是同一实验。

## 诊断结论与M2范围

1. 当前最值得优化的是推荐与复用推荐的首页；其次菜谱列表的N+1。相同权重反复计算是明确的Python热点，2N查询产生可测量往返成本。
2. 先在一次请求内计算一次历史权重，再批量读取本用户菜谱/食材，保持原规则、完整响应、排序、分页及用户隔离。不引入跨用户缓存、不削减必要约束。
3. 长请求在并发时长期占用连接；先缩短工作，再重测池等待。此时扩池可能放大竞争，不作为M2首选。无迁移索引需求的可靠证据，不为展示而增加索引。
4. M2使用同样数据/资源/原API配置、对应负载和重复运行，报告SQL/EXPLAIN/错误率及耗时。结果是否更快由实测决定；M1不预报收益比例。
