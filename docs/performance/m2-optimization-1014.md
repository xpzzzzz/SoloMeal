# M2：MySQL读取与推荐计算优化（2026-10-14）

本阶段已完成：性能对照、数据完整性、SQLite及真实MySQL回归均已验证，按用户连续授权进入M3。

## 问题、选择与改动

[M1基线](m1-baseline-1014.md)测出推荐29+2N SQL，以及每候选重复计算同一历史的衰减权重。500菜谱时profile约78%的累计时间在 `_weights`。因此本阶段仅修改四个业务文件：

- `services/food.py`：共享原单菜谱的序列化函数；新增两次查询的批量读取，校验每个请求ID都属于当前用户，缺失/跨用户仍404，保持输入顺序、重复ID和食材排序。
- `services/planning.py`：批量装配完整菜谱；历史权重每请求计算一次并传给候选评分，不改变硬约束、价格、评分或排序。
- `services/personalization.py`：支持请求内预计算权重，旧单候选调用仍可自行计算。没有全局缓存。
- `api/food.py`：第一页ID查询后批量读取，原分页、反馈和响应字段不变。

没有修改连接池、索引、API进程数、事务、库存扣减、幂等或用户身份。代码选择以减少重复工作为目的，不通过减少候选/返回数据改善指标。

## 限流对照的失败

同一10菜谱/20用户混合场景，直连API全部成功；Nginx在优化后记录979次200和3518次429（失败率78.23%，Locust退出1），原轮609次全200。观察到成功完成21.92RPS，总完成100.67RPS包含大量快速拒绝，不能将其作为性能收益。原20次/秒、burst80的限制未调整；优化后请求完成更快，循环负载也随之加快，拒绝进一步改变了端点完成比例。报告保留失败，不通过放宽限流让结果全绿。
