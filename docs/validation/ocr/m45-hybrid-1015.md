# M4.5：CPU OCR、按需视觉辅助与人工核对（2026-10-15）

本阶段已完成实现与专项验证，按连续授权进入M5。付费/真实模型调用0；原18080/18088未替换，未提交推送。生产默认仍为`vlm_only`，OCR需显式开启；没有足够真实样本证明混合模式更好。

## 实现与业务边界

`receipt_ocr.py`延迟加载PaddleOCR CPU，仅使用PP-OCRv5移动检测/识别模型，保留文本、顺序、置信度及文字框。`receipt_rules.py`保守提取名称、数量、单位、规格、购买份数与明确小计，复用原Schema、单位归一和数量校验。约重、范围、未知包装份数、负数和非法数量保持未知；只有名称而缺少数字的行也保留核对，避免静默漏项。

`receipt_recognition.py`实现三模式。明确有效的OCR不调用VLM；缺失/歧义/低置信度按需辅助。模型输出继续原字段与业务校验，数量/金额冲突留空，名称和行数冲突附两种解释供用户核对。高置信度不代表包装数量已确定。OCR异常时hybrid可转VLM，ocr_only保持本地语义并明确失败；两者不可用仍能手动编辑。VLM失败保留私有OCR证据但任务显示失败。

模式在受理时固定到原Celery任务，结果与证据写MySQL；图片由Worker只读访问。新增迁移`f1b7d9e31015`，原任务默认vlm_only，未传mode的幂等请求保留旧payload摘要。仍须逐项人工核对、保存并确认后原子入库；任务本身不能写库存。界面增加模式、识别路径、冲突提示及可展开的OCR核对信息。

## CPU依赖与兼容性

- PaddlePaddle3.3.1 CPU、PaddleOCR3.7.0、PaddleX3.7.2，仅ocr-core依赖；[Linux完整解析版本](resolved-linux.lock)。未安装GPU/Torch/all扩展，原API虚拟环境没有安装OCR。
- Windows CPython3.13 AMD64的CPU wheel及与原锁定包的依赖解析通过，见[解析证据](windows-compatibility.json)。原生DLL/完整推理未验证；Windows开发通过Linux Docker Worker执行。
- Linux Python3.13.15实际导入、Paddle CPU数学检查及18次OCR/模式运行通过，CUDA编译false。实验镜像`solomeal-ocr:compat-1015-01`，digest `0abc1395d9b59a000d3f6571c79f8d7d1cdbff68e783c03697be3f3d8f15a453`，限制2 CPU/2GiB。系统库为libgomp1、libglib2.0-0、libgl1。
- 首次从官方BOS下载检测/识别模型，私有缓存保存两套inference.json/pdiparams/yml。M5再整理正式镜像、模型取得与干净启动步骤。

## 真实Worker与页面

复用独立18110/18111项目，移除M4短租约故障overlay，使用真实MySQL/RabbitMQ/Celery和实际CPU OCR；VLM仅封闭合成Oracle，未配置网络模型。见[8场景结果](worker-workflows-1015.json)：

- 三模式、约重和未知包装均可核对；API202受理16.6～31.1ms，首个冷Worker任务约7.17秒，其余为具体场景观测值，不是延迟保证。
- 注入低置信度并让Mock给冲突数量，形成草稿但数量留空、显示1处冲突。
- 注入OCR失败，hybrid转Mock；双方失败/辅助失败均明确failed，辅助失败仍保留私有OCR。
- 八场景未确认库存及事件始终0。
- 真实浏览器[2/2通过](browser-1015.json)：本地识别500ml/750g，人工逐项取消待核对标记并保存后才新增2批次/2事件；冲突页面数量空、确认禁用、原始OCR可展开。截图只保存在私有目录。
