## 原因与改动

第77节第三轮的工具正确返回缺鸡蛋，但模型仍建议生成做饭预览。SYSTEM已经多次要求避免这种表述；执行层prepare_cooking也已检查库存，因此此次是展示出口与执行能力不一致，不是少了一条提示或库存能被超扣。

新增recommendation-response-v1：当本轮最后一条工具执行为成功的recommend_meal，最终展示回答由服务端从该工具结果生成，逐菜列出当前人数、用量、缺口、整包报价和后续动作。can_cook_now必须为true、shopping为空且预算状态允许，才标记可请求做饭预览。否则说明先购买并确认入库，再重新查询。库存足够的表述限定为查询时，不承诺未来可执行。

run.result保存message、response_source、source_step和逐菜next_actions，原模型最终文字另存model_message作证据。run.messages及后续历史保存实际展示的服务端回答；原工具记录不改。不是用关键词删除坏句，也没有额外模型修复请求。页面标明推荐及下一步来自查询结果，保留换行；带tool_calls的中间说明不作为最终回答展示或收入新历史摘录。历史run不回写。

next_actions是展示元数据，不是授权令牌，也没有自动入库/做饭按钮。prepare_cooking及批准时的现有业务校验保持不变；测试直接调用缺料预览仍得到INSUFFICIENT_STOCK且pending为空。

## 边界

- 仅覆盖紧随成功recommend_meal的最终回答。后续工具失败时不复用更早成功结果；其他工具的自由文本仍待另行处理。本次不宣称全面解决自然语言忠实性。
- 不解析用户自由文本来决定菜谱，不自动选择、不猜份数。推荐原始条件/工具参数准确性仍依赖Agent；模板无法修复错误条件提取。
- 服务端模板代替这一出口的自由回答，表达灵活性减少；模型原文和产品展示必须分别评审，不能把模板通过算成模型语义提升。未来真实诊断必须留存并分别评分model_message与message，不沿用只评分单个最终文字的口径冒充新盲测。
- 当前状态是查询快照，没有新增跨请求锁或库存预留。历史回看不表示现在仍可做；真正预览/确认仍重新查库。
- SYSTEM、工具schema、模型预算、数据库迁移、私有.env及冻结评测JSON未编辑。源码指纹变化，不能复用旧批次登记。
