# SoloMeal 功能扩展开发与逐项审查计划

版本：2026-09-21 v1。性质：待执行开发规格，不是完成报告。

## 0. 执行契约与范围

本计划依据用户本轮要求：新增功能服务于可操作、可演示的简历项目；每项功能完成后交回主审查 agent，审查通过才进入下一项。一次针对性验证通过即收口，不开展无边界审计、多轮 stress、研究型模型评测或重复证据归档。发现具体问题才修复并复测受影响部分。

开发 agent 每次只领取下表一个阶段。一个阶段必须同时交付数据库/接口/前端入口/必要测试/可访问预览（按该阶段实际需要），不能以“API 已完成、页面以后补”报完成。阶段内部自行完成例行技术选择，不反复向用户请求已经明确的授权。

本轮只制定计划，不自动创建执行任务、不改业务代码、不启动模型调用或部署。后续用户把任务交给执行 agent 后，该 agent 按本计划执行相应阶段。本计划提出的模型调用上限是待执行时的预算建议，不把写入计划等同于已批准付费调用。旧试用环境 18080、旧私有评测目录与历史分数保持原口径；不以新功能开发为理由重新开启旧验收工作。

### 0.2 审查状态

每阶段状态仅为 `TODO → IN_PROGRESS → READY_FOR_REVIEW → CHANGES_REQUESTED / APPROVED`。只有主审查 agent 可填 APPROVED；开发 agent 自测通过只能填 READY_FOR_REVIEW。审查修复在当前阶段完成，不自动启动下一项。

用户在页面试用与代码审查可以并行；用户明确报告本阶段功能不能操作时不能标 APPROVED。无需等待独立第三方试用、多人评分或论文式效果评估。

## 1. 已核对的实现基础与限制

- Web 应用位于 `backend/app` 与 `frontend/src`；根下 `src/` 是另一套插件实现，其按份库存与在线 tuning 规则不能直接移植为 Web 的克/ml/个数量规则。
- `backend/app/services/planning.py`：按时间、厨具、排除食材等约束筛选；评分为库存覆盖×60＋临期覆盖×40－近期重复×10，采购成本默认权重 0，可由请求设置。沿用现有预算/报价完整性排序优先级，再用扩展后的分数排序。
- `Recipe` 已有 servings/minutes/equipment/steps/source/version；`RecipeIngredient` 绑定用户自己的 Ingredient，用量为 Decimal。基础食材单位 g/ml/piece，输入可用 kg/l 转换。
- `CookingRecord` 有菜谱快照、servings、status、created_at，当前没有实际耗时或真正开始时刻。快照包含 recipe version；旧记录缺失新增字段时必须能正常读取。
- `food.run_operation` 已提供业务操作幂等机制，已有乐观版本检查、用户隔离与库存事务；新业务复用，不再实现第二套库存扣减。
- `plans` 是现有单菜计划/预览，不把它直接改成多菜自动排餐。
- `shopping.create` 当前从单个计划生成清单；`shopping.change(..., confirm)` 会真正创建库存批次。新“已买”状态必须与确认入库区分。
- 前端为 React＋TypeScript＋Vite，入口集中在 `main.tsx`。新面板单独建组件，沿用会话失效、请求错误、幂等重试习惯。
- 既有列表分页必须完整处理；统计、画像、合并采购不能只使用前端第一页的 100 行。
- 2026-09-21 本次只读检查见三个既有 `.pytest-purchase-contract-*` 未跟踪目录及权限警告。不得清理、改 ACL 或称当前树完全无残留；交接只列本阶段变更。

代码路径是定位提示；执行前读实际代码。接口命名允许小幅调整，但业务行为、计算口径、权限、前端入口不能悄悄改。必要偏差在交接写清原因和最终契约。

## 2. 共通工程与前端要求

### 2.1 数据与接口

1. 新表/新增列用 Alembic 迁移；兼容既有 MySQL 与测试用数据库。旧记录补默认值，不伪造反馈、耗时或历史菜谱标签。
2. 所有写入与读取按当前登录用户限制；关联 ID 必须验证所属用户，不信任请求中的 user_id。
3. 需要原子提交的动作复用现有事务入口；修改业务状态用 expected_version。带副作用的确认操作带 Idempotency-Key；同键同请求返回既有结果，同键异请求沿用冲突语义。
4. 原有 API 默认字段行为向后兼容；新增响应字段允许增加。新开关以服务端存储为准，不只存在浏览器。
5. 小数使用 Decimal，沿用已有数量换算和取整。不能直接相加 g/ml/piece，不能假设一个鸡蛋等于固定克数。
6. 不修改旧评分器、冻结协议或历史证据来适配新功能；新契约测试独立命名。已有冻结检查若与新版本确实冲突，列出明确差异供主审查处理，不能删除断言或把旧失败写成通过。

### 2.2 每阶段用户必须能操作

- 新入口中文可见；有空态、加载态、错误态、成功反馈；错误就近显示，用户可以改正后重试。
- 挂载 GET 不能覆盖用户已经编辑的输入。列表刷新不能重挂载正在编辑的表单或丢失草稿。
- 切账号清理该用户页面状态与计时草稿；旧请求返回不能写入新账号页面。
- 关键提交期间禁用重复点击，但最终仍由后端幂等保证。网络失败保留输入与同一逻辑操作键。
- 桌面和约 390px 宽窗口各确认一次主要操作可见，无需完整设备矩阵。
- 生成、推荐、预览、收藏、计时都不扣库存。只有原有明确“确认做饭”路径扣库存，原有“确认入库”路径增加库存。
- 新算法所需时间均按服务端 UTC 计算；按天显示/统计采用 Asia/Shanghai，响应明确时区，避免浏览器时区改变样本窗口。

### 2.3 预览与部署交付

默认使用一个专属、持续复用的功能预览 Compose 项目，例如 `solomeal-features-0921`，目标端口 18088（先检查占用；冲突则选空闲端口并记录实际地址）。独立数据库和图片卷，不能引用源 18080 的卷。复用现有部署脚本和构建配置。

执行 agent 领取 F1 后准备这个环境；后续阶段迁移/更新同一预览环境，保留用户在预览环境录入的反馈，不每阶段重建空库。凭据按现有私有配置方式保存，不提交仓库、不写入报告。若环境创建受到文件系统或工具权限限制，只请求该具体权限。

每阶段交接必须写：实际完整 URL、构建对应 commit 或工作树说明、服务健康结果、登录方式（不在文档写密码）、页面点击路径、3～6 步试用步骤。验证页面实际加载新版标识，而非只看 Docker healthy。开发模式可作为 Docker 不可用时的替代，但要提供实际持续可用的 URL 和启动方式，并明确是开发服务器。

不得只交截图、测试 fixture 页面或 `dist` 文件。审查时页面必须能够连接持久化后端实际操作。没有环境资源时标出这个具体阻塞，不能谎称可试用。

源 18080 更新不属于每阶段默认动作。待最终审查后如用户要求替换试用环境，再备份和部署；不需要为了每个阶段单独发布 Release。

## 3. F1：菜谱发现、草稿审核与入库

### 3.1 页面流程

菜谱页新增“发现菜谱”；推荐结果不足 3 条时显示“当前有 N 道符合条件的菜谱，发现更多”。候选充足时仍可由用户主动进入发现页。初版不在查询推荐时自动调用模型。

发现表单包含人数（默认偏好）、时间上限、现有厨具、不可放宽的排除食材、可选需求文字（最多 500 字）、优先使用库存食材（默认开）。用户点“生成候选”后，一次最多返回 3 道；逐道编辑、显示校验错误、“确认加入菜谱库”或“丢弃”。加入后提供“用当前条件重新推荐”，继续使用原条件，不自动放宽。

用户可手动创建同形状的候选草稿；模型未配置时明确告知，仍可编辑手工草稿。演示 mock 只能用于自动测试/明确标记的演示数据，不能冒充真实生成。

### 3.2 数据建议

- `RecipeDiscoveryBatch`：id/user_id/request_key/request_hash/status(pending/completed/failed)/constraints/model_name/usage/error_code/created_at。唯一(user_id, request_key)。usage 允许 null，不能用估计值冒充实际 token。
- `RecipeDraft`：id/user_id/batch_id(nullable)/version/status(draft/accepted/discarded)/payload/validation_errors/validation_warnings/source_type(llm/manual/external)/source_ref/accepted_recipe_id(nullable)/created_at/updated_at。
- payload：name、servings、minutes、equipment、steps、ingredients[{name, quantity, unit, optional, resolved_ingredient_id?}]。烹饪标签在 F2 增加；未知值保留可编辑文本，不伪造正式 ID。
- 正式 Recipe 增加 source_type（旧记录默认 manual，表示原录入方式，不推断原始作者）、source_ref(nullable)。保持旧 source 文本兼容。LLM 来源只写模型名/生成时间，不伪造外部 URL。
- 草稿保存允许字段不完整；正式转换必须走完整的强类型 RecipeInput 校验。不要因一行“适量”就让整批候选无法在页面展示。

### 3.3 校验和转换的精确规则

1. name/人数/时间/厨具/步骤/食材数量沿用 RecipeInput 现有范围：人数 1～10，时间 1～480，厨具 1～15，步骤 1～30，每步不超过 500 字，食材 1～40，至少一种必选食材。
2. quantity 必须是有限正数，数量精度和上限沿用 Quantity。unit 只接受 g/kg/ml/l/piece；kg→g、l→ml；piece 遵循现有整数约束。碗、勺、适量不猜换算，标注字段错误等待修改，optional 也不能以此绕过数量要求。
3. 食材名用现有 normalize/resolve 及当前用户别名匹配。已存在 ID 时验证归属和单位维度。重复 canonical ingredient 行提示合并，首版不静默合并 required/optional 冲突。
4. 无匹配食材时页面展示“将新建：名称，基础单位”。用户确认菜谱时，在同一事务中创建这些食材及菜谱；单位不兼容时要求改行或选择正确食材，不能自动修改旧食材单位。
5. 生成请求包含排除食材、厨具、人数、时间。返回不符合发现条件的候选保留草稿，标出 `constraint_mismatch`，默认不允许以“符合本次条件”身份加入推荐。用户可显式修改条件或修正草稿；用户存储的排除条件不能由模型覆盖。
6. 对步骤出现的“已有食材名/别名或有限厨具词表”做简单一致性提示：明确出现却未列清单则警告。此检查只是字符串启发式，不宣称完整语义校验；不增加第二次 LLM 审查。用户可补清单或确认已核对警告。
7. 同名菜谱已存在显示重复提示；同一草稿 accepted 后再次确认返回已创建菜谱，不再新建。首版不做向量相似查重。
8. 确认时重新校验当前食材/偏好和草稿版本，在原子事务中创建新食材、Recipe、RecipeIngredient，设置 accepted_recipe_id。失败全部回滚。丢弃草稿不影响库存或正式菜谱。

### 3.4 模型与 Agent 边界

- 首版只实现 LLM provider 和手工草稿；预留小型 provider 接口，不实现通用网页爬虫或外部数据源采购。external 只是预留来源类型，不在页面假装已经接通搜索。
- 复用现有服务端模型配置和传输；输出约定 JSON 候选，解析失败显示可重试错误。不得从模型返回执行工具、代码、SQL 或任意 URL 请求。
- 每次用户点击最多一个模型请求、最多 3 候选；不自动修复重试、不自动循环发现。上下文仅含当前条件与最多 30 个相关库存名称/数量/单位，不发送整个历史、账号信息或 token。
- discovery 独立调用预算建议输出最多 3000 token、沿用当前 30 秒超时（按实际传输能力核对）；不修改旧 Agent 全局预算。截断/超时保持失败，用户可以显式重试。
- batch 状态先持久化，再在数据库事务外调用网络。重复同 request_key 不重复调用；失败或进程中断结果未知时不自动再调用。用户点重试产生新 key，并明确可能有新的调用成本。无需引入队列或守护服务。
- 本阶段页面按钮直接调 discovery service。现有 Agent 的 recommend_meal 仍只读，不塞入隐式付费调用。需要对话入口时可在本阶段提供“打开菜谱发现”操作链接；自动发现工具另作后续扩展，不是 F1 完成门槛。
- 真实功能冒烟预算建议最多 2 次调用：一次生成，一次仅在首次技术失败时由用户决定是否重试。执行前确认本批已有调用授权；没有授权先完成全部离线实现与预览，精确汇报剩余真实验证，不能把 mock 通过写成真实生成通过。

### 3.5 接口建议

`POST /api/v1/recipe-discoveries`（幂等 key）；`GET /recipe-discoveries/{id}`；`GET/POST /recipe-drafts`；`GET/PUT /recipe-drafts/{id}`；`POST /recipe-drafts/{id}/validate`（只读校验）；`POST .../accept`；`POST .../discard`。修改/确认带 expected_version。列表沿用分页。

### 3.6 本阶段最低验证

- 一条合法候选经编辑确认后出现在真实菜谱页，并能进入现有推荐/做饭预览。
- “鸡蛋适量”“g 与 ml 冲突”“人数 0”分别定位到字段；修正后可确认。
- accepted 草稿重复确认只有一个正式菜谱；创建食材失败不留下半条菜谱；另一用户不能读取/确认草稿。
- 模型关闭/超时显示清楚错误且保留条件；生成/校验/入库都不改库存。
- 一条浏览器路径覆盖生成（测试可注入 provider）→修改→确认→重新推荐；真实模型调用按前述单次预算。

## 4. F2：收藏、反馈与烹饪标签

### 4.1 行为与数据

新增 `RecipeFeedback`：user_id/recipe_id/favorite(bool default false)/rating(neutral/like/dislike default neutral)/version/updated_at，唯一(user_id, recipe_id)。favorite 和 rating 独立：收藏代表想保存，不强制等于喜欢。接口返回当前状态，刷新后不丢失。

菜谱详情/卡片提供收藏按钮与“喜欢/不喜欢/清除评价”。收藏列表复用菜谱页过滤。重复同状态设置不累加次数；切换状态替换旧状态。删除菜谱清理反馈关联，不删除用餐快照。

Recipe 新增 `cooking_methods`：枚举 stir_fry/steam/boil/stew/bake/pan_fry/cold/other，0～3 个去重值；旧记录 []，不自动用模型补历史标签。手工菜谱、发现草稿、编辑器均可选择中文标签。改变标签按现有菜谱编辑机制递增 version，历史快照不回填。

本阶段明确不改变排序（排序在 F5）；按钮旁说明“评价已保存”，不要提前声称已训练模型。菜谱快照增加标签；老快照读取默认 []。

接口建议：`PUT /recipes/{id}/feedback` 传完整 favorite/rating 与 expected_version（首次 0）；`GET /recipes/{id}/feedback`，菜谱列表可包含 feedback 字段避免 N+1。

### 4.2 验证与试用

收藏→收藏筛选可见→刷新仍在；喜欢→不喜欢→清除的状态正确；其他用户不受影响；删除菜谱不导致历史列表报错。一个浏览器流程即可覆盖。提交审查后停在 F2。

## 5. F3：做饭模式与实际耗时记录

### 5.1 最小交互

菜谱详情与推荐卡片新增“开始做饭”：选择人数/是否含可选食材，显示用量、步骤、当前步骤号、上一步/下一步、已完成步骤、总计时、暂停/继续、结束。

开始/步骤勾选/暂停均不调用扣库存接口。用户点“结束并确认做饭”时展示实际耗时（可修改或选择不记录），再调用现有 cook/plan confirm 事务；成功才展示用餐记录。库存不足或版本冲突保留计时与步骤，让用户处理后重试，不能提前写 completed 记录。

仅浏览菜谱时也允许退出，不强迫完成。直接沿用原有确认做饭按钮的路径继续可用，耗时为空。

### 5.2 计时算法

页面状态：user_id/recipe_id/recipe_version/servings/include_optional/current_step/completed_steps/accumulated_ms/running_since_ms/state(running/paused)/operation_key。

显示有效毫秒 = accumulated_ms ＋（running 时 max(0, Date.now()-running_since_ms)，否则 0）。暂停先把差值加入 accumulated_ms 再清 running_since；继续设置新的 running_since；setInterval 只负责刷新显示，不能每秒累加作为真值。

刷新/后台停留期间 running 状态继续计时，暂停期间不计时。以用户＋菜谱＋版本为 key 写 localStorage，登出清当前用户计时状态；不保存 token。恢复时提示“发现未完成计时，继续/丢弃”。首版仅承诺单标签页计时，多标签不自动同步；后端确认仍由同一 operation_key 防重复。

实际分钟默认 `max(1, ceil(elapsed_ms/60000))`，提交前可改整数 1～480 或清空。计时越界不截断冒充真实值：提示手填合法值或不记录。系统时钟跳变导致异常时允许手动改正，不开发后台计时服务。

### 5.3 数据与接口

CookingRecord 加 `actual_minutes nullable int(1..480)`、`duration_source nullable(timer/manual)`、`feedback_version default 1`。有 actual_minutes 必须有 source，无值则 source=null。标准时间和人数只取记录快照/servings。

CookingInput 和 ConfirmPlanInput 增加可选 actual_minutes/duration_source，现有调用不传则 null。cook 成功时原子写入；相同幂等键请求不能另生一次记录。新增 `PUT /cooking/{id}/duration`（actual_minutes 可为 null、source、expected_version）只修改反馈，不重复扣库存、不改变 created_at。

历史页每条 completed 记录可“填写/修改用时”；已撤销记录可展示旧用时但禁止修改，F4/F5 不计入。旧快照缺 version 的记录只展示、不参与个人耗时匹配。

### 5.4 验证

可控时钟验证运行 2 分钟＋暂停 5 分钟＋运行 3 分钟得到 5 分钟；刷新继续；结束一次生成一条记录并仅扣一次库存；历史修改只改用时；撤销原功能正常。前端必须在移动宽度可点到暂停和确认。

## 6. F4：个人耗时估计（固定可复算规则）

### 6.1 样本范围

仅当前用户、completed、actual_minutes 非空，且快照 recipe_id/version 与当前菜谱完全一致、servings 等于本次人数的记录。取近 180 天内最近 20 条，排序 created_at 降序、id 降序。撤销记录、无 version 旧记录、别的菜谱/人数/用户不计入。

不把时间正比于人数外推；改菜谱后新版本从标准时间开始。合法范围内的异常反馈不偷偷删除；中位数减小其影响，用户可在历史页修正/清空。

### 6.2 公式

令 T=菜谱标准分钟数，n=有效样本数，M=实际分钟数中位数（偶数取中间两项平均）。

- n=0：estimated_minutes=T，weight=0，median=null，source=standard。
- n>0：`weight = min(0.8, n/(n+3))`。
- `estimated_minutes = ceil((1-weight)*T + weight*M)`；保留内部精度，最终只向上取整一次。
- source=personalized，返回 sample_count、sample_median、weight、standard_minutes、estimated_minutes、recipe_version、servings。

例：T=20，所有样本均 30 分钟：n=1→weight=.25→23；n=3→.5→25；n=9→.75→28；n=12→.8→28；以后权重不超过 .8。T=20，样本[20,30]：M=25、weight=.4、预计22。

这些是 v1 产品规则，非训练得出的最优参数；集中定义常量并测试上述数值，不在文案宣称准确率提升。

### 6.3 接入

UserPreference 增加 personal_time_enabled，默认 true；页面开关可关闭。关闭时筛选与展示使用标准时间（可另显示有历史数据），服务端返回有效 source=standard_disabled。

recommend 的 TIME_LIMIT 判断改用有效 estimated_minutes，等于上限允许；菜谱本身 minutes 不覆盖。推荐卡显示“标准20分钟 / 你的预计25分钟，基于3次记录”；0 样本显示“标准20分钟，暂无个人记录”。

所有调用 recommend 的计划创建/修订/确认检查采用同一函数；若现有计划 freshness 快照遗漏个人耗时或偏好输入，补入必要的有效估计/开关/画像版本或指纹，确保预览后修改反馈不悄悄确认过期条件。不在本阶段重写整个计划机制。

### 6.4 验证

公式例子、0样本回退、偶数中位数、版本/人数/用户隔离、撤销后 n 减少；预计25遇上限24被拒、25通过；关闭个人时间恢复标准筛选。浏览器修改用时→重新推荐能看见估计和候选变化。

## 7. F5：隐式偏好与解释

### 7.1 信号与特征

推荐使用当前用户最近 90 天最多 200 条 completed 记录（created_at/id 降序）。已撤销不参与。只读取实际使用的必选食材，以及快照 include_optional=true 时的可选食材。排除 is_staple=true 的食材；旧快照缺 is_staple 时可用仍存在且属于本用户的食材属性，否则默认普通食材并在算法实现注明兼容口径。

每条记录行为权重 `w=2^(-age_days/30)`，age_days=max(0, UTC时间差秒/86400)。同一 recipe_id 在同一个上海自然日最多贡献一条（取最新），减少误触重复与当天批量记录影响。特征集合是 canonical ingredient_id 与 cooking_methods，使用集合去重，不能因为数量多而增加偏好权重。

令 W=sum(w)。某食材支持率 `p_i=sum(w where i appears)/W`；某烹饪方式支持率 `p_m` 同理。W=0 时全为0。

候选食材 affinity_I 是候选实际参与规划的非 staple 食材 p_i 的算术平均；方式 affinity_M 是候选 cooking_methods 的 p_m 平均。两类都有：affinity=.7*I+.3*M；只有一类：取该类；均没有：0。

历史置信权重 `c=min(1,N/5)`，N 为去重后有效完成记录数。隐式偏好分 `implicit_points=10*c*affinity`，范围[0,10]。没有历史为0，不能填默认“喜欢”。

### 7.2 显式反馈与最终分数

本菜谱 explicit_points：favorite=true 加3；rating=like 加5；rating=dislike 则 explicit_points=-15（忽略收藏加分）；neutral 不加评价分。喜欢与收藏合计最多8。

`preference_points=clamp(implicit_points+explicit_points,-15,15)`。

`final_score=existing_base_score+preference_points`。沿用原来排序中预算未知/报价完整性的优先级和稳定 ID 决胜；只替换分数位置。近期重复惩罚仍由原逻辑保留。

不喜欢只降低这道菜的排名，不把它所有食材都推断为禁忌，也不硬过滤。需要绝对排除的食材仍去偏好设置。点“换一道”、浏览、未做的计划均不产生负向信号。

personalization_enabled 默认 true；关闭时 preference_points=0，恢复原分数；个人时间开关独立，不联动关闭。请求中的 Agent 不能修改用户存储的这两个开关。

### 7.3 输出与页面

推荐返回原有 score_components 加 personalization 对象：enabled、history_count、ingredient_affinity、method_affinity、confidence、implicit_points、explicit_points、preference_points、最多2条主要依据。前端用文字解释，不展示一屏算法数字。

“最近5次完成记录中3次使用鸡肉”必须用该响应的真实窗口和去重计数生成；衰减分数与原始次数分别标明，不能混用。不足5条写“基于2次记录，偏好仍在积累”。提供偏好摘要页面/区域与个性化开关，不提供虚假的“训练中”。

首版请求时批量查询并计算，避免每候选扫描数据库；无需画像表、向量库、训练任务或 LLM 总结。

### 7.4 固定验收例子

冻结 now，5条不同日期完成记录且均含鸡肉，候选无方式标签且仅鸡肉：N=5、affinity=1、implicit=10；同样候选仅1条：implicit=2；无历史0。收藏＋喜欢最高与 implicit 合计封顶15；dislike 按定义减15后总分可能仍含 implicit，但不能超过无 dislike 时。

还需验证撤销/可选食材未使用不计入、不同用户隔离、关闭恢复原分、硬约束不被高分突破。浏览器收藏/评价/完成记录改变后重新推荐显示新理由；用种子测试数据演示时明确标注为演示历史，不宣称真实用户效果。

## 8. F6：推荐场景、解释、换一道

### 8.1 预设参数

| 场景 | inventory | expiry | repetition | purchase_cost | 时间 |
|---|---:|---:|---:|---:|---|
| 默认 | 60 | 40 | 10 | 0 | 用户当前值 |
| 清冰箱 | 40 | 80 | 10 | 0 | 用户当前值 |
| 快速做 | 60 | 40 | 10 | 0 | min(当前值,20) |
| 少买东西 | 100 | 20 | 10 | 0 | 用户当前值 |
| 换换口味 | 60 | 40 | 30 | 0 | 用户当前值 |

预设是显式表单参数，不修改保存的用户偏好。用户切场景重新从其当前手动基线构建，避免快速做的20分钟意外残留到所有模式。手动调整后标记“自定义”，返回“默认”恢复当前用户的正常值。

“少买东西”模式额外在可行性优先级之后、final_score之前按 missing_ingredient_count 升序排序，再按分数；缺口种类少不等于价格低，不宣称最低价。此模式必须由服务端识别，不能只重排前端前三条。缺口为0排在有缺口之前。

### 8.2 解释与换一道

推荐卡展示标准/个人时间、库存覆盖（现有按食材行比例的指标，文案“食材满足度”，不冒称重量占比）、最多2项推荐原因、是否需采购。缺报价显示“价格未知/估价不完整”，不显示0元。

“换一道”只在本次结果里跳过当前 recipe_id，按同一排序取下一条未显示候选；不重复已跳过 ID、不写 feedback、不调用模型。参数变更或用户点“重新推荐”重置跳过集合。耗尽显示“本次候选已看完”，提供重置/调整条件/发现菜谱，不暗中循环。

硬约束无候选时展示按原因聚合的数量和可操作入口，比如缺厨具/超时；不可自动删除排除食材或改人数。避免把多个排除原因之和说成不同菜谱总数。

验证每个预设参数一次、少买东西排序一例、换一道耗尽/重置一例、无候选发现入口一例。核心浏览器场景可合并。

## 9. F7：多菜合并采购

### 9.1 页面与输入

菜谱/推荐卡“加入采购组合”，组合篮允许1～10个不同菜谱，每道人数1～10，include_optional独立。同一菜谱重复添加聚焦已有行，用户改人数，不重复建行。选择后点“计算采购”生成只读预览，展示每种食材总需求、有效库存、缺口、整包数量/估价及各菜贡献。

不要复用单菜 MealPlan ID 冒充多菜计划。接口建议 `POST /shopping/combined-preview` 和 `POST /shopping/combined`；预览无写入。输入 recipe_id/version/servings/include_optional，组合预算可选。

### 9.2 算法

逐菜使用现有 selected_lines/required_quantities，归一到 ingredient基础单位后累加 `required_i=sum(required_i_each_recipe)`。可用库存按现有规划规则排除 archived/已过期批次，`available_i=sum(quantity)`；只减一次，`missing_i=max(0, required_i-available_i)`。

例：菜A鸡蛋2个、菜B鸡蛋3个、库存3个→总需5、缺2。若每包6个/6元，则购买1包、6个、估价6元，不按各菜分别整包取整。两菜分别需米100g/200g，库存150g→缺150g。不跨单位维度换算。

报价沿用保存的来源/日期与30天有效性；过期/缺失报价保持 unknown，已知费用只是下界，不宣称预算满足。已知费用超过组合预算可提示超预算；实际购买确认仍用现有预算规则。

### 9.3 持久化和已有购物功能兼容

ShoppingList.origin 新增 discriminator：旧数据缺 kind 按 single_plan；新组合 kind=recipe_combination，含菜谱版本/人数/可选标记、预览需求、库存及报价快照。检查所有直接 origin['plan_id'] 的旧代码（尤其 shopping.create 的去重循环），改为兼容分支，不能让组合清单弄坏单菜清单。

预览返回签名，签名覆盖本次相关菜谱版本、有效库存量/批次版本、报价、组合条件；确认创建清单时服务端重算并比较，变化返回可刷新预览的冲突，不悄悄用旧量。新清单创建复用幂等机制，创建不扣库存、不预留库存。

每行“已买”是独立检查状态，可置在 ShoppingList 的单独 checked_ingredient_ids JSON 列（默认[]），避免未知字段破坏既有 PurchaseItem 校验。更新带清单版本，不创建库存批次。

“确认入库”继续是现有显式业务操作，按钮旁写清将增加库存；先核对实际数量/成本/有效期等。第一版只支持整张清单确认，不做分批入库：要求全部行已买；没有购买的行可显式移除后再确认，移除不代表已经满足原菜谱。旧单菜清单原有流程不强制补勾选，新组合才要求。

用小票另行入库后，不能再把同一批实物重复确认到组合清单。首版提供“已通过其他方式入库，关闭清单”的无库存写入操作/取消说明，不做自动小票关联匹配。清单有完成/关闭状态，阻止再次确认。

### 9.4 验证

鸡蛋5-3=2例；不同单位归一；过期库存不计；整包只算一次；库存变化预览失效；旧单菜清单仍可建立/确认；勾选不改库存、确认仅加一次；不同用户组合拒绝。浏览器选两道→预览→保存→勾选→核对→确认入库。

## 10. F8：今天首页

登录默认进入“今天”；保留库存/菜谱/推荐/采购/助手/偏好入口。首页四块：

1. 优先处理：未来3天内到期、未归档且quantity>0的批次，最多5条，按日期/名称排序。过期批次单独标“已过期，需检查”，不能推荐吃掉。日期是用户记录，不展示为食品安全保证。
2. 今天推荐：按当前偏好显示前三条、场景按钮、个人时间、原因、开始做饭/换一道/收藏。用现有 recommend 服务，不写第二套算法。
3. 待采购：未完成清单最多3张、待买条数，点击进入F7或既有清单。没有选菜时不凭空生成采购缺口。
4. 最近做过：最近5条completed记录，菜名/日期/人数/实际耗时，点击历史详情可修改耗时。撤销记录不计入完成数。

数据可通过一个轻量 home 聚合端点或并发已有请求获取；统计在服务端跨分页聚合。一个区块失败可局部重试，不把整个首页变成空白。首页加载绝不自动生成菜谱或调用模型。

空账户给出“添加库存/发现菜谱/安装示例”的入口；安装示例必须用户点选，不能混成用户真实历史。移动版纵向排列，关键按钮不横向溢出。用一条首页→发现/收藏→开始做饭→历史的人工/自动浏览器流程验证导航与刷新。

## 11. F9：日历与个人统计（增强项）

统计页月历按 Asia/Shanghai 将 completed.created_at 分组，点击日期看菜谱快照/人数/耗时。月份默认当前，可前后切换，不为每一天单独发请求。

本月指标：完成做饭次数（记录数，注明非天数）、做饭天数、常做菜Top5（recipe_id聚合，删除菜谱仍用历史名称）、已记录实际用时的次数与分钟合计。没有用时的数据不按0分钟加入平均；展示样本数。个人耗时趋势按同菜谱版本＋人数分组，至少2条才画趋势，否则列记录。

不显示没有真实数据支持的“节省金额”“减少浪费重量”“营养达标率”。推荐估价不能当实际消费；库存减少不能直接当减少浪费。

只做月范围聚合接口与简单日历/列表，不引入BI系统。验证月边界时区、撤销排除、空月、旧菜谱删除后的历史可读。
