# SoloMeal：从需求到可靠业务闭环

> 写作视角：假设项目交付后，由开发者回顾设计过程。以下用真实设计和问题支撑叙述；尚未完成的最终验收不会写成已完成，简历版本采用截至 2026-09-17 可证实的成果。

## 1. 我先把“一人食管理”拆成可以验证的需求

用户说“帮我管理一个人吃饭”，我首先明确三个问题：家里有什么、今天能做什么、做完后还剩什么。再加入时间、厨具、忌口和预算，把流程确定为：**库存录入 → 推荐菜谱 → 补齐缺料 → 确认做饭 → 库存扣减 → 必要时撤销**。

例如，“我有 300 克米，今晚想做一份饭”，验收不能只看模型是否给出菜名，还要检查用量是否可行、确认前库存是否不变、重复点击是否只扣一次、撤销是否恢复原批次。首版聚焦单餐闭环，暂不扩展自动下单、多日计划和多 Agent 协作。

项目以开源 meal-manager 为起点。我先审查其食材归一化、菜谱规则、存储和测试：原插件以 JSON 和近似“菜份”管理数据，不能直接变成多用户的克数库存。因此保留上游归属和 GPL-3.0，参考已有领域语义，另建独立 Web 后端、数据库和前端；旧“菜份”不强行换算成克。

## 2. 先让业务算得对，再让模型参与

技术栈选择 **Python、FastAPI、Pydantic、SQLAlchemy、MySQL、Alembic；React、TypeScript、Vite；SSE、Docker Compose；pytest、Playwright、GitHub Actions**。聊天和小票分别接入可配置的文本、视觉模型，模型请求通过 HTTP 适配层处理。

关系型数据库适合表达用户、食材批次、方案版本、采购、小票和消耗明细，也能提供事务约束。前后端分离方便手机使用和独立测试。Agent 使用显式状态机：当前流程主要是查询、生成方案、等待确认和恢复，暂不需要引入 LangGraph；避免框架检查点和业务数据库同时管理一份状态。

我先实现确定性业务服务：按时间、厨具、忌口、份数筛选菜谱，再计算缺料和采购成本。例如缺米 190 克、每包 100 克且 3 元，实际支出是买两包的 6 元；报价缺失或过期时不能承诺满足预算。这样即使模型不可用，用户仍能手工管理库存和完成做饭流程。

## 3. 用真实故障反推设计边界

| 发现的问题 | 我的定位与取舍 | 解决与验证 |
|---|---|---|
| 用户双击确认、网络重试，或者两个页面同时做饭，可能重复扣减或超扣 | 问题在服务端一致性，禁用按钮只能改善体验 | 用 MySQL 短事务、并发锁、绑定用户和请求参数的幂等键统一提交；保存批次消耗明细，撤销按原明细恢复。真实 MySQL 工程验收覆盖故障回滚与竞争，冻结工程场景 60/60 通过 |
| 模型把编造的价格来源、日期传入工具，工具又把它当事实返回 | 仅要求“不要编造”不够，工具参数本身授予了模型制造事实的能力 | 去掉 Agent 可写的报价字段，价格只取服务端保存记录；新增按明确缺口计算的只读工具，不让模型猜份数。用非法字段反例和真实诊断验证边界 |
| 用户把一份改成两份，工具算对了，模型却复述上一轮用量；缺料时仍建议做饭 | 分别检查本轮工具输出、历史消息和最终正文，发现“调用成功”不等于“回答正确” | 历史作为文本摘录，本轮工具结果单独处理；推荐出口由服务端依据当前候选生成展示文字和后续动作，保留模型原文单独评审。四轮诊断通过，但不据此宣称整体模型能力达标 |
| 手机点击小票确认没有明显反馈 | 查看请求发现 HTTP 422：某行的“个”与食材的“克”冲突；错误只显示在长页顶部 | 增加逐行单位／整数校验、操作区错误提示及入库中状态；先跑前端与浏览器回归，再让用户真机复验。视觉结果先成为可编辑草稿，人工确认后才入库 |

这些修复遵循同一条路径：**保留失败 → 找最小复现 → 判断是模型、接口、数据还是交互问题 → 修改对应边界 → 用反例和真实路径复验**。例如 MySQL 返回 JSON 的键顺序变化曾导致历史摘要重复嵌套，最终修复的是结构比较逻辑，而不是继续调整提示词。

## 4. 把“能演示”推进到“可恢复、可解释”

我把会话、运行状态和工具事件持久化，用运行租约约束重复执行，用 SSE 向页面传递状态；刷新后重新读取服务端状态，写操作仍经过显式确认。模型调用期间不持有数据库锁，避免把外部服务延迟变成业务锁等待。

验证分层进行：纯规则测试检查计算，真实 MySQL 检查事务和竞争，浏览器检查用户闭环，真机检查实际交互。模型评测比较固定流程、直接模型和 Agent＋工具，同时记录任务成功、回答忠实性、延迟与成本。

这里也发现过评测本身的问题：题干只说缺米 190 克，执行器却额外要求“三份菜谱”。我先核对题干、工具和评分契约，再建立独立版本的采购协议，不通过改旧分数掩盖失败。历史合成留出成绩仍是 48/60，低于 85% 门槛；局部修复通过不能替代新版本的整体验收。

交付侧已验证本地 Compose 空环境启动、模型关闭降级、MySQL 与私有小票图片联合恢复，恢复前后 21 张表摘要及图片字节一致。完整交付还需完成恢复异常演练、新主机验收和演示材料，这些是最终收尾项。

## 5. 我怎样合理使用 AI

**产品中的 AI：** 负责理解自然语言、选择受限工具、识别小票和组织解释；数量、预算、权限与写入由确定性服务负责。模型可以提出操作，用户确认和服务端校验决定是否执行。

**开发中的 AI：** 我负责需求边界、架构取舍、验收标准和最终审查；让 Codex 等 coding agent 辅助阅读上游、起草接口和页面、实现限定模块、补反例测试、分析日志及整理文档。每次交付一个可检查的小任务，例如：“复现重复确认，保证同键同参重放只返回原结果，同键异参拒绝，并提供数据库验证”。

我不会把 AI 生成的代码或“测试通过”的总结直接当结论，而是检查实际差异、命令结果和业务数据；测试使用隔离环境，模型诊断预先限定次数并记录配置。AI 可以做初步语义评审，用户表达清晰度仍由真人评价。反思是：前期多轮补提示和重复诊断消耗不少精力，更有效的做法是尽早收紧工具权限、明确事实来源和评分契约。

## 6. 简历怎么写

**SoloMeal 一人食智能管理系统｜独立开发 / Agent 与后端**  
**2026.09—至今**（正式完成后填写实际结束月份）

**项目简介：** 面向独居用户库存难跟踪、饮食决策与采购执行脱节的问题，基于开源 meal-manager 改造独立 Web 应用，构建“库存—推荐—采购—做饭—撤销”闭环，通过单 Agent 工具调用连接自然语言需求与可校验的业务操作。

**技术栈：** Python、FastAPI、Pydantic、SQLAlchemy、MySQL、Alembic、React、TypeScript、SSE、Docker Compose、pytest、Playwright

**1. 库存事务与操作一致性：** 针对重复确认、并发做饭与撤销恢复可能导致的重复扣减和超扣，设计批次库存、消耗明细及版本化方案，基于 MySQL 事务、并发锁和用户／请求参数绑定的幂等机制完成确认与补偿；在真实 MySQL 上通过冻结工程场景 **60/60**，覆盖并发竞争、故障回滚和重复撤销。

**2. Agent 状态与工具边界：** 针对模型编造报价、复用旧轮用量及提出不可执行操作的问题，构建持久化 session/run/工具事件与显式确认状态机，以运行租约支持执行治理，通过 SSE 同步页面状态；限制报价只来自服务端记录，隔离历史与当前工具结果，并在推荐出口按实际候选生成后续动作，保留模型原文供独立评审。

**3. 评测驱动的问题定位与交付：** 建立 **60 个工程场景＋20 个 Agent 调试场景＋20 个合成留出场景** 的分层评测，比较固定流程、直接模型和 Agent＋工具，绑定配置及输入证据并保留失败；结合真实 MySQL、浏览器与安卓试用定位跨层缺陷，完成本地 Compose 部署及数据库／私有图片联合恢复验证。

### 面试时的一分钟讲法

“我从一人食的实际流程出发，先解决库存、数量和确认写入，再接入单 Agent。最有代表性的问题是，模型曾把编造的报价日期传给工具，工具又把它返回成事实。我检查调用链后，发现根因是工具允许模型填写本应由服务端掌握的信息，于是删除这部分参数，让报价只来自保存记录，并补非法输入与真实恢复验证。整个项目里，我用 coding agent 加快实现和排查，自己负责问题拆解、设计取舍及验收。项目的价值是把模型的不确定输出接入有明确权限、事务和恢复机制的业务流程。”

简历优先展示“具体问题—设计选择—验证结果”。不要写未经测量的节省时间比例、生产并发能力，也不要把工程 60/60 写成 Agent 成功率 100%；本项目未使用 LangGraph、Redis、RAG 或 MCP，不为技术栈数量添加它们。
