## 0. 项目目标与执行原则

项目：`https://github.com/xpzzzzz/SoloMeal`

本次改造的目标不是增加更多 AI 功能，而是强化 SoloMeal 在 Python 后端开发方面的工程能力，最终形成三条能够用于技术面试的完整链路：

1. **性能优化链路：** 业务访问量与数据规模增加 → 压测定位瓶颈 → SQL/索引/查询优化 → 前后性能对照。
2. **异步任务链路：** 小票视觉解析耗时 → Celery + RabbitMQ 解耦 → Worker 独立处理 → 任务持久化与可靠恢复。
3. **工程交付链路：** 功能开发 → 自动化测试 → GitHub Actions → Docker Compose 可复现部署。

新增 OCR 需求用于改善小票文字提取与字段解析，并验证是否能减少不必要的视觉模型调用；不预先承诺准确率或成本收益。OCR（光学字符识别，将图片中的文字转为文本）与 Vision LLM/VLM（能理解图片的视觉大模型）在 M4.5 实现，异步执行继续依托 M3/M4 的可靠任务链路。

本次明确不引入 Redis、Prometheus、Grafana、Kubernetes、微服务拆分及其他不必要的新技术。

### 全局执行约束

- 按 **M0 → M1 → M2 → M3 → M4 → M4.5（PaddleOCR + Vision LLM）→ M5** 的顺序执行。
- **一次推进一个里程碑，完成验证和结果报告后按最新授权继续下一阶段，直至额度耗尽或 M5 完成。**

- 优先复用现有代码，避免重写事务、库存、幂等和小票状态管理。
- 不调用真实大模型、不使用付费 API，使用 Mock/Stub 完成相关测试。M4.5 也可回放保存的已授权响应；未来如需真实付费模型，必须另行取得用户明确确认。

- 任何指标都必须由真实执行产生，不能编造优化收益。

## M3：P2 — Celery + RabbitMQ 异步小票解析

**目标：把耗时的视觉解析从 HTTP 请求主链路中移到独立 Worker，同时保留原有小票业务规则。**

### 1. 技术选型

采用：

- FastAPI：接收上传和解析请求。
- RabbitMQ：任务消息代理。
- Celery：独立后台任务执行。
- MySQL：小票业务状态、任务状态和持久化结果。
- Docker Compose：启动 API、数据库、RabbitMQ、Worker 等组件。

本阶段不增加 Redis，也不依赖 Redis 结果后端。

优先复用现有 `ReceiptImport`、解析状态、版本校验、操作幂等以及用户每日限额逻辑。

### 2. 设计新的请求链路

预期流程：

用户上传小票 → 发起解析 → FastAPI 完成参数与权限校验 → 持久化待执行任务 → RabbitMQ 接收消息 → Celery Worker 执行视觉解析 → MySQL 保存结果 → 前端获取解析状态 → 用户审核后确认入库。

解析请求应快速返回已受理状态，不再一直等待视觉模型完成。

使用现有小票详情查询能力读取执行状态，必要时增加轻量轮询。

明确区分 `queued`、`running/parsing`、`parsed`、`failed` 等状态，并考虑原有历史记录的兼容性。

### 3. 保证任务投递可靠

重点解决：

**数据库保存成功，但 RabbitMQ 消息投递失败怎么办？**

设计持久化待投递机制，推荐最小可行的 Transactional Outbox 或等效的数据库持久待派发方案。

要求：

- 待派发记录与业务受理状态在同一数据库事务中持久化。
- 独立派发逻辑将任务发送至 RabbitMQ。
- RabbitMQ 不可用时任务不能直接丢失。
- 发送成功但确认状态未更新时，允许重复派发，并依赖幂等消费保护业务。
- RabbitMQ 使用持久队列和持久消息，并检查发布确认机制。
- 不允许使用仅存在于 API 进程内存中的任务列表作为可靠任务来源。

优先采用简单、可解释的方案，不引入额外服务。

### 4. 独立 Worker 处理

Celery Worker 应当：

- 按任务 ID 读取 MySQL 中的真实任务。
- 从受保护的共享上传卷读取原图，不通过 RabbitMQ 传递图片二进制或 API Key。
- 使用现有视觉模型解析器和结构化数据校验。
- 保存解析结果或明确的失败状态。
- 释放数据库连接，不得在等待外部模型响应期间长期持有数据库行锁。
- 限制并发数、执行时间和重试次数。
- 记录必要的任务 ID、状态和脱敏错误类别。

保留现有人工修改、确认入库和取消功能。

### 5. 前端适配

修改现有 `ReceiptPanel.tsx`：

- 点击自动识别后展示“排队中”或“识别中”。
- 可以手动刷新或有限频率轮询。
- 完成后展示可编辑草稿。
- 失败后展示清晰错误和可执行的后续操作。
- 页面刷新或重新登录后仍然能够恢复任务状态。
- 未经用户审核，不允许自动入库。

沿用现有接口和页面组织方式，避免重新开发另一套小票页面。

### 6. API 兼容性

先检查现有 `POST /receipts/{id}/parse` 的响应契约。

如果改为异步受理返回，需要明确处理 HTTP 状态码、响应字段和前端兼容。

不允许在没有同步更新测试与前端调用逻辑的情况下改变接口。

### M3 交付

- Celery + RabbitMQ 实现代码。
- 必要的 Alembic 数据库迁移。
- Docker Compose Worker/Broker 配置。
- API 和前端改动。

## M4：P2 — 消息队列可靠性和故障恢复

**目标：证明这条异步处理链路不仅能工作，而且遇到异常时不会丢任务、重复产生结果或误写库存。**

### 必测异常场景

1. 用户重复点击识别：同一业务操作不产生多个有效解析任务。
2. 相同任务消息重复投递：Worker 不重复提交最终业务结果。
3. Worker 执行中退出：任务可以重新派发或恢复，不永久卡在运行中。
4. RabbitMQ 暂时不可用：数据库已受理的任务不会静默丢失。
5. 视觉模型超时：有限重试，达到限制后进入明确失败状态。
6. 视觉模型返回非法数据：不能写入正式库存。
7. 解析期间用户修改或取消草稿：旧解析结果不能覆盖用户更新。
8. API 返回丢失后客户端重试：使用原操作键查询或返回已有状态，不重复创建任务。
9. 不同用户请求：任务与图片严格隔离。
10. 识别成功但未人工确认：库存和采购数据不发生变化。

### 技术要求

- 明确 Celery 消息确认时机和重投策略。
- 不以关闭消息确认机制来规避重复消费。
- Worker 获取执行权时有明确的状态检查或租约机制。
- Worker 意外退出后，过期执行权可以被安全恢复。
- 不能因为多个 Worker 同时收到相同任务而并发提交解析结果。
- 重试必须有次数和时间边界，不能无限调用模型。
- 最终失败要可查看、可诊断。
- 不得假称 RabbitMQ + Celery 能自动提供业务层“恰好执行一次”保证。
- 保留原有用户确认后的 MySQL 原子入库、行锁和幂等逻辑。

### 测试方法

同时使用：

- pytest 单元测试。
- Mock 模型异常注入。
- 真正的 RabbitMQ + Celery Worker 集成测试。
- 必要的容器停止、重启和消息重复投递测试。
- Playwright 页面状态恢复测试。

不能只使用 Celery eager 模式或 Mock Broker，就宣称消息队列可靠性已通过。

不需要运行真实付费视觉模型。

### M4 交付

生成《RabbitMQ/Celery 可靠性验证报告》，列出：

- 测试场景。
- 测试输入。
- 故障注入方法。
- 实际结果。
- 重试及恢复过程。
- 业务数据库最终状态。
- 未覆盖的风险。

**M4 的核心验收条件是：不能发生重复入库、任务静默丢失或不可解释的永久卡死。**

## M4.5：PaddleOCR + Vision LLM 混合小票识别

**目标：建立“小票图片 → PaddleOCR 文字提取 → 字段解析与业务校验 → 按需 VLM 辅助 → 可编辑草稿 → 人工确认入库”的完整链路，并如实比较三种识别模式。**

**进入条件：M4 已完成，可靠性报告已交付，用户已确认进入 M4.5。此前不安装或接入 OCR、不开发字段解析与模式切换、不提前开展本阶段测试。**

### 1. 业务背景与阶段边界

普通超市小票包含大量结构化文字。完全依赖 VLM 可能增加模型调用成本，商品名称、包装规格、数量和金额仍可能解析错误。引入本地 OCR 与轻量规则，先处理字段明确的内容；不能可靠解析的部分再按需交给 VLM 辅助，最后仍由用户逐项核对。

M0～M4 继续执行原目标。M3/M4 先以现有视觉解析器和 Mock 完成异步正常链路与可靠性验证，不因 OCR 补充扩大前置阶段。

M4.5 完成识别实现、字段解析、异常降级、Worker 集成、必要前端适配及本阶段验证。M5 再统一收口正式 Docker 依赖、GitHub Actions 和 README；M4.5 的隔离兼容性验证不能拖到 M5 才首次执行。

### 2. CPU 依赖兼容性检查

优先采用 **PaddleOCR CPU 版本**，不强制 GPU。

在本阶段开始后、接入业务代码前，先在隔离的 Windows 开发环境和 Linux Docker 测试环境中验证：

- Python、PaddleOCR、CPU 推理运行时及相关依赖的版本与兼容性。
- 安装、导入、模型加载与最小图片识别是否可运行；记录命令、结果与失败情况。
- OCR 模型版本、权重取得方式、本地缓存及无网络启动条件。
- 初始加载与实际识别的耗时、内存及 Worker 并发限制，依据实测选择合理配置。

不直接向现有开发环境或正在使用的容器加入未经验证的大型依赖组合。兼容性不成立时报告具体阻塞与可行方案，不假称可部署，也不为了完成阶段强行改为依赖 GPU。

### 3. OCR 输出与数据隐私

保留必要的 OCR 原始信息，便于用户核对和问题定位：

- 识别文本。
- 行顺序。
- 识别置信度。
- 必要的文字位置或边界框。

图片、OCR 文本、解析字段及 VLM 响应均按用户私有数据处理，复用现有权限与用户隔离；不得写入公开日志、公开 CI 产物或公开测试报告。运行日志只记录必要任务 ID、状态、耗时与脱敏错误类别。可公开或入库的测试材料必须是合成数据、充分脱敏数据或明确获准使用的材料。

### 4. 轻量字段解析与业务校验

基于 OCR 文本、行顺序和必要位置建立轻量规则，识别：

- 商品名称。
- 购买数量与单位。
- 包装规格、单包装净含量及包装数量。
- 商品金额，明确区分商品金额、单价和整单合计。

复用现有单位归一、Pydantic Schema（结构化字段校验）及小票业务校验，不重新实现库存逻辑。缺失或无法唯一解释的字段保留未知及原因；不能根据金额反推未经证实的数量，不能用默认数值补齐后伪装识别成功。

明确区分包装数、每包净含量与可入库总量。多包装或约重商品无法确定实际数量时，必须保留待核对状态；“约重”不得当作精确称重值。

### 5. OCR 优先、VLM 按需兜底

混合模式的决策规则如下：

| 条件 | 处理结果 |
|---|---|
| 普通小票字段明确、数量有可靠依据且通过原有校验 | 直接形成待审核的可编辑草稿，无需调用 VLM |
| OCR 置信度低、字段缺失、包装数量存在歧义或校验失败 | 在 VLM 可用且调用获准时辅助解析，记录触发原因 |
| OCR 置信度高，但数量语义仍不确定 | 保留不确定性；置信度不能替代数量证据 |
| VLM 给出解析结果 | 同样经过现有字段与业务校验，非法结果不能作为确定值 |
| OCR 与 VLM 字段冲突 | 保留候选来源、冲突与待核对状态，交给用户处理，不静默覆盖为确定值 |
| OCR 无法运行，VLM 已配置且调用获准 | 可降级到原有视觉识别，明确展示实际识别路径及 OCR 失败 |
| VLM 不可用、调用未获准或辅助失败 | 显示实际失败或未解决字段，保留有效草稿内容及手动修改能力 |
| OCR 与 VLM 均不可用，或没有可用识别结果 | 明确自动识别失败，保留手动录入入口，不伪装成功 |

低置信度只是兜底触发条件之一。阈值与字段完整性判定在本阶段结合样本确定并记录，不把高置信度等同于业务正确。

### 6. 三种识别模式

支持 **ocr_only**、**vlm_only**、**hybrid**：

| 模式 | 执行路径与对照边界 |
|---|---|
| ocr_only | 只执行 OCR、规则解析与校验；有歧义时保留待核对，失败时支持手动录入，不隐式调用 VLM |
| vlm_only | 复用原有视觉解析与校验，作为对照基线 |
| hybrid | OCR 优先，符合兜底条件时按需调用 VLM；OCR 运行失败时可明确降级至原视觉识别 |

任务及报告记录请求模式、实际执行路径、兜底原因与失败类别。显式 ocr_only 的纯模式边界用于保证对照有效；用户切换模式另按原有操作规则执行。

**正式默认模式由实际测试证据决定，不预先认定 hybrid 更好。** 若样本或授权响应不足以支持可信效果对照，明确记录“默认模式待定”及所缺证据，保留现有默认行为，不宣称新默认方案已验证。

### 7. Celery Worker 集成与可靠性复用

OCR 与 VLM 解析统一在 M3/M4 建立的 **Celery Worker** 内执行，沿用 RabbitMQ、MySQL 任务状态、持久待派发、重试及故障恢复机制，不另建异步任务系统，不把耗时识别移回 HTTP 主链路。

- 通过既有任务 ID、受保护图片卷和用户归属读取输入，不在消息中传递图片二进制、识别正文或 API Key。
- 复用执行权、租约、重复投递保护、版本校验和旧结果拒绝机制。
- OCR 初始化、识别、VLM 辅助均有执行时间与资源边界；复用并核对既有有限重试策略，避免 OCR/VLM 两层叠加无限重试。
- 记录每次尝试和 VLM 调用；不把业务结果幂等解释为外部模型调用绝不重复。
- 解析过程中不长期持有数据库行锁；识别结束后按原有规则保存草稿或失败状态。
- 针对 OCR 或 VLM 执行中 Worker 退出、重复消息及恢复后结果提交补充必要验证，证明原 M4 可靠性保护仍适用于新增解析路径。

### 8. 保持小票业务规则与必要前端适配

保持现有业务规则：

- 识别结果只能进入可编辑草稿。
- 用户必须逐项核对后才能确认入库。
- 未确认时不得写入库存或采购业务数据。
- 保留版本校验、操作幂等、用户隔离、取消及整单原子入库能力。
- 用户编辑或取消后，较早识别任务不得覆盖新状态。
- 不确定字段必须得到人工核对并通过原有校验后才能入库。

沿用现有 ReceiptPanel.tsx 和 M3 状态恢复方式，补充必要的模式选择、识别路径/降级状态、字段来源、缺失/歧义/冲突提示及原图/OCR 信息核对能力。保留排队、识别、失败、刷新恢复与手动录入入口，不重新开发另一套小票页面。

### 9. 可重复的小规模测试集与三模式对照

先建立固定样本清单、人工参考字段、预期不确定项及重复运行脚本，覆盖：

1. 清晰普通小票。
2. 模糊或低质量图片。
3. 多包装商品。
4. 约重商品。
5. 金额缺失。

另外通过异常注入覆盖 OCR 无法运行、VLM 超时/失败/非法响应、双方字段冲突、两种识别能力均不可用；验证失败状态真实、草稿可编辑、手动录入可用和未确认零入库。

同一测试集分别运行三种模式，报告至少记录：

| 指标 | 统计要求 |
|---|---|
| 商品名称、数量、单位、商品金额的字段准确情况 | 逐字段对照参考值，报告正确/错误/缺失/不确定/不适用及分母；未知参考值不算正确 |
| 用户需要修正的字段数量 | 记录人工参考对照所需修正数，区分必须补填与冲突核对；如仅模拟核对，明确说明 |
| 单张小票处理耗时 | 记录逐样本结果、硬件、版本、冷/热启动；区分排队、OCR、规则解析与 VLM 阶段 |
| VLM 调用次数 | 记录实际外部调用、Mock 调用与保存响应回放次数，包含失败和重试；不能混为同一成本指标 |
| Token 用量 | 能获取时记录实际或已授权响应中的原始用量与来源；无法获取标未知，不估造 |
| OCR/VLM 失败与冲突处理 | 保留失败样本、实际状态、降级路径和人工后续操作，不能只汇总成功样本 |

默认用 Mock VLM 或保存的已授权响应进行测试，**未经用户明确确认，不调用付费模型**。使用 Mock/回放时，本轮真实外部 VLM 调用为 0；其耗时不代表真实模型服务耗时，历史 Token 也不是本轮新增用量。

可用现有样本做回归，但必须注明其来源、是否曾用于调试及代表性限制；不能把已用于调试的样本当作独立留出证据。如果现有样本或响应无法支持可信效果比较，如实列出缺口，不编造准确率、成本下降比例或默认模式优势，也不据此改写既有小票验收结论。

### 10. 自动化验证与阶段验收

执行必要的解析规则单测、三模式路由与兜底测试、现有 Schema/单位校验回归、真实 OCR CPU 冒烟、真实 Celery/RabbitMQ 集成及前端核对/失败恢复测试。OCR Mock 只能验证流程，不能替代真实 PaddleOCR 可运行性验证；VLM Mock/授权回放不能证明真实模型准确率。

验收需证明：

- 明确且有效的 OCR 结果能够直接形成草稿；歧义、高置信度但数量不确定、非法响应与冲突均不被伪装为确定值。
- 三模式边界与降级路径可复现，OCR/VLM 全不可用时可手动录入。
- 新识别路径保持版本、幂等、隔离、取消、原子入库及未确认不写库存等保护。
- Windows 与 Linux CPU 兼容性有实际验证记录，失败和未覆盖项如实披露。
- 对照报告与自动化结果能重复运行，已知限制及未获模型授权导致的验证缺口明确列出。
