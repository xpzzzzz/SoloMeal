# Mem0 真实连接复用与延迟验证

2026-10-28（Asia/Shanghai）。**本次在隔离测试项目的一个已清理合成用户上进行了六次真实、只读 Mem0 搜索。**六次均为 HTTP 200、返回零条；跟踪在第一次观察到一次 TCP 建立和一次 TLS 启动，后五次均发出了 HTTP/1.1 请求且没有新的 TCP/TLS 建立事件。在本次连接连续存活的范围内，证据支持“观察到连接复用”。没有执行新建 Client 对照，因此不能据此量化复用相对于逐次新建客户端的性能收益，也不能推断长期生产延迟。

## 环境、安全检查与方法

- 实验使用 Windows 本机、Python 3.13.13、HTTPX 0.28.1、httpcore 1.0.9；独立应用实例和第五阶段的合成 SQLite 数据库以 `mode=ro` 打开。未启动长期服务。数据库中按此前实验的唯一标记确定的合成账号仅一条，开启了个性化。没有读取或输出其他用户的记忆。
- 凭据非空，隔离项目归属来自用户此前明确确认及[真实 A/B 报告](mem0-real-ab-report.md)；本轮只检查私有配置文件时间早于该实验的证据、当前进程无密钥环境覆盖，不输出密钥、项目标识或其他敏感配置。本轮没有再次访问项目管理接口，不能从本次响应独立重证项目身份。
- 第五阶段记录该用户的合成记忆已删除且列表和搜索复查为空。实验前以只读方式检查本次合成数据库的记忆操作，`unknown/pending/mutating` 为 0；同时对本机七个匹配既有 Mem0 合成实验目录且包含 operations 表的数据库做只读汇总，未决数均为 0。这不是对所有生产数据库的审计。
- 使用当前应用的真实 `MemoryProvider`，在独立进程的同一个 `create_app()` 实例中临时启用 Provider；未修改 `.env` 或普通应用开关。配置读取的阶段超时为 **2 秒**，与代码默认值一致，没有使用此前实验的 10 秒覆盖。无 Agent、模型、写入、修改或删除请求。
- 合成用户 ID 只从该只读数据库在服务端取得，传给现有 `read_memories()`；每次重新建立 SQLAlchemy session，以该应用实例中的同一个 Provider 查询。此次没有登录或发送 SoloMeal 推荐 HTTP 请求，因此 `read_memories` 耗时不是用户浏览器端到端推荐耗时，也没有重新开展推荐 A/B。
- 在该独立进程中，仅为观测给 Provider 实例装载临时包装：使用真实 `_request` 和 `_get_client`，为这个真实 HTTPX Client 安装 request/response hooks，把 httpcore `trace` 限于连接建立和发送请求头事件；只保留事件名称、时间及 HTTP 状态，不保存 callback 中的地址、请求、响应或异常对象。所有六次沿用 Provider 原有的固定搜索文本、服务端用户过滤、top_k 和 threshold。若响应封套异常、结果非空或出现非搜索请求，包装会在进一步归属 GET 前停止；没有放宽归属校验。
- 测试中没有按时限反复请求失败的重试：六次按计划各一次，未出现失败。测试过程关闭可能包含请求细节的 HTTPX/httpcore 日志；没有记录认证头、完整 URL、用户 ID、原始查询或记忆文本。事件内容以脱敏计数和耗时记录于本报告；没有保存原始 HTTP trace 或响应正文。

执行前还核对了当前 [memory.py](../backend/app/services/memory.py) 中的应用实例级客户端、锁和 Cookie 拒收策略，以及 [main.py](../backend/app/main.py) 的 lifespan 关闭路径。[第七阶段离线报告](mem0-latency-optimization-report.md)记录了 MockTransport 下复用、跨用户配置隔离及正常/异常关闭测试；本次真实运行结束时观察到 Provider 客户端引用已清空，结合当前 `close()` 代码路径及此前测试支持资源关闭，**本次没有单独保存 Client `is_closed` 的观测**。

## 本次逐次真实观测

时间为毫秒，保留三位小数。`HTTPX` 是客户端 `request()` 加状态检查的时间，包含网络、远端等待与响应收包；`搜索包装` 从进入生产 `_request()` 到返回 JSON，包含首次 Client 创建；`记忆读取` 是 `read_memories()` 本身；`读取外层` 还包括本次诊断脚本创建和关闭数据库 session。它们互相嵌套，不能相加。表中 TCP/TLS 时间是相应 httpcore 事件开始到完成的墙钟时间，仅在恰有一次完整事件时可计算。

每次都观察到一次请求头发送事件、一次 HTTPX 请求尝试，`read_status=empty`，无超时阶段或异常；所有响应均为 HTTP/1.1。汇总为 TCP 建立事件 **1 次**、TLS 启动事件 **1 次**；在本次单 Client、串行、连续成功且每次都记录到请求发送的观测中，后五次 **5/5 与既有连接复用一致**。该判断基于事件序列和实际请求，不能仅由 Client 对象相同得出；它不保证其他并发、空闲间隔、代理或服务端连接关闭情况下也不会重连。trace 没有保留具体连接 ID，也不区分代理连接与最终远端连接，故不声称掌握网络拓扑。

后五次的 HTTPX 耗时中位数为 **551.099 ms**、搜索包装中位数 **551.143 ms**、`read_memories` 中位数 **552.088 ms**。首次较慢，且发生连接建立；但冷请求和后续热请求的条件不同，没有新建 Client 的平行对照，不能把差值直接归因为复用，也不能说它与历史 1.4 秒 A/B 数值构成有效的优化前后实验。服务端处理时间、DNS 独立耗时、单独网络往返时间均**未知**。

首次 `connect_tcp` 事件耗时 3344.966 ms，大于配置的 2 秒。该事件在当前 httpcore 同步后端包围 `socket.create_connection`，并非可单独分离的某一次网络阶段纯耗时；可能涉及地址解析、多个候选地址或调度，本轮没有细分证据。2 秒配置是 HTTPX 连接/读取/写入/连接池等待的阶段超时，并非事件、整个 HTTP 请求或整个业务读取的严格墙钟截止；本次首次读取约 5.21 秒仍成功，不足以确定默认配置在其他网络条件下的可靠性。没有为本测试调整超时，也没有主动制造超时。

- 逐次新建 Client 对照：**未执行**。为了限制非必要真实请求，本轮在取得连接 trace 后没有继续发送额外请求；因此没有同环境、同期、同样查询的冷连接对照，也无法计算复用的因果收益。未调整生产实现以构造对照。

## 结论、风险与下一步

**已实测：**当前真实 Provider 在本次单进程、单合成用户、短间隔的六次连续读取中复用了底层连接；默认 2 秒阶段配置下六次均成功，后五次读取中位数为 552.088 ms。**离线已测：**客户端生命周期、并发配置隔离和 Cookie 保护，见第七阶段报告；这不等于本轮在真实服务上做了并发压力测试。**尚未证明：**与新建 Client 相比的延迟改善、服务端时间、生产成功率或推荐质量变化。

现有五次热连接仍约 0.53～0.58 秒的 `read_memories` 墙钟，说明仅复用连接并未消除远端读取成本；但样本少、只有空结果、同一时段与同一用户，不能据此估计一般分布。HTTPX Client 无法保证服务端持续 keep-alive；空闲过期、网络中断或代理可能触发正常重连。未知写入的人工核销和旧索引/在途请求风险仍存在，本轮只读测试没有验证它们。

下一步最小建议是**先保留现有实现并继续使用脱敏分段指标**；若需要判断是否再优化，应在另获授权后，用独立合成账号和有限请求预算，在同一时间窗口预先固定顺序，比较冷启动和后续请求、真实连接事件及逐次新建 Client 对照，同时记录空/非空结果、失败和服务可用性。不能通过直接比较本次首次与后五次宣称提速；也不建议据此调整评分、搜索阈值或引入缓存。未改 P8、既有 A/B 证据、生产应用配置或部署；未提交或推送。
