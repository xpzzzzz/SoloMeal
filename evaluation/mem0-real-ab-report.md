# SoloMeal 真实 Mem0 推荐 A/B 对照报告

> 公开副本：合成记录 UUID 和运行标记已替换为稳定匿名标签；原始证据保存在本机。

2026-10-28（Asia/Shanghai）。本轮在用户确认的隔离 Mem0 测试项目中，使用**一个合成用户、四条真实写入的合成记忆和八个固定场景**完成对照。四条记忆均已删除并复查。结果支持记忆评分在这组合成夹具中按预期改变排序；**不支持推断真实用户总体推荐质量已提升或存在统计显著性**。

## 实验环境与冻结方案

- 本轮开始前只读检查正在运行的 `solomeal-features-0921` 数据库和四个此前合成数据库，未决记忆操作均为 0；普通应用的 Mem0 开关仍关闭。隔离测试项目身份由用户在前序确认，测试前 ping 亦返回项目标识。本轮使用新建的独立 SQLite、一个新合成用户及独立应用测试进程；不读取或修改真实用户记忆。
- 偏好建议由已有 `Scripted` 测试模型产生，经该用户的 Agent 运行与确认 API 写入真实 Mem0；没有真实 Agent/付费模型调用。B 组每次通过真实 Mem0 搜索及当前适配器取得记忆，**没有用 Fake/Mock 或人工补充记忆**。A 组在同一进程内仅将 Provider 关闭，未发远端请求。
- 写入前固定 [协议与八场景](mem0-real-ab-protocol.json)，SHA-256 `0ca44898dfc9e7baaf10f4b04379f70096c423defcda7f425edf83eacfd43344`。协议中的 `{run}` 仅替换为唯一合成标识；运行后核对嵌入证据的协议与该文件一致。固定方案包括正向食材、负向烹饪方式、20 分钟倾向及一个无关食材，各一条；负向偏好仅为软扣分，忌口由既有硬约束管理。
- 12 道固定合成菜、同一库存与用户偏好贯穿所有场景；各场景可设不同时间和厨具条件，但每个 A/B 配对的用户、请求、菜谱、库存、报价、硬约束和其余配置相同。配对顺序交替为 A→B、B→A。实验未改推荐引擎、±6 上限、事务或 P8 冻结协议。
- 协议固定后进行了仅本地夹具预演（没有 Mem0 请求），检查目标在 S1 基线 Top-3 外、S3 基线已在 Top-3、S4/S5 的候选及 S8 无候选，以及四类硬约束夹具。没有根据预演或真实结果修改期望。
- [脱敏逐次证据](mem0-real-ab-evidence.json)包含合成记录 ID、各候选分数、理由、检索结果、约束检查及逐次请求耗时，不含 API Key 或真实用户记忆。运行器为 本机运行器，[分析器](mem0_real_ab_analyze.py)可从证据复算指标。真实运行须显式 `--execute-real`，且在再次使用前仍需独立确认项目及未决操作；`--setup-only` 仅预演本地夹具。
- 指标复算使用 `backend/.venv/Scripts/python.exe evaluation/mem0_real_ab_analyze.py evaluation/mem0-real-ab-evidence.json`；已另行验证每组候选和原始分相同、A 组每场景远端请求为 0、B 组为 1、记忆分有界、总调用及清理状态。运行后只调整了运行器的退出状态和预算不足时的部分完成标记，不影响本次已记录的样本、评分或协议；最终运行器的本地预演和 Ruff 检查通过。

S4 和 S5 检索到了无关 `ghost` 偏好，但候选无对应字段匹配，得分及完整排序没有变化；S8 没有候选，空结果相同但不能作为有候选时稳定性的独立证据。S7 两组分别正确拒绝 `forbidden`、`too_slow`、`wrong_equipment` 和 `too_expensive`，对应忌口、时间、厨具和**已知**预算超限。报告不把报价未知的情况称为已验证预算通过。

## 预定义指标与解释

- **综合偏好 Top-3：A 2/5（40%），B 5/5（100%）；Top-1：A 0/5，B 3/5（60%）。**分母为 S1、S2、S3、S6、S7；正向场景以目标在前 N 名为命中，S2 负向场景以不喜欢的目标不在前 N 名为命中。S4/S5 无目标，S8 无候选，均不进入分母。
- 如只看四个正向目标场景 S1/S3/S6/S7，Top-3 是 **A 2/4、B 4/4**，Top-1 是 **A 0/4、B 2/4**；负向 S2 从 A 的 Top-1/Top-3 不符合预期，变为 B 两者均符合。S3 的基线已有 Top-3 命中。
- **指定相关记忆检索：5/5 场景返回。**八次 B 组搜索均返回本用户四条结构化记忆（32/32 个预置记录的场景观测）；其中无关 `ghost` 记忆也在 **8/8** 次返回。该固定查询会返回未匹配候选的记录，因此不能把 5/5 当作精准率，也不能据此证明检索对不同请求具有良好的相关性区分。
- **硬约束违规率：A 0/25、B 0/25 候选观测。**25 是八个场景中返回候选的累计数，同一菜在多个场景重复计数，并非 25 个独立菜谱或用户。
- **无关或无匹配导致的意外排序变化：0/2 个有候选的无匹配场景**（S4、S5）。S8 双方无候选，另行记录。因为其他场景同时存在相关偏好，不能把该结果外推为对所有候选或所有查询的因果证明。
- 本实验只有一个合成用户、同一批菜谱和一次成对请求；S1/S2 条件及候选高度重叠，S7 也与其他场景共享数据。比例只描述这五个预定义场景，不能作为独立用户样本的准确率、显著性或真实世界收益。

## 请求数、延迟与成本

共 **32 次真实 Mem0 HTTP 请求**，低于 60 次上限：ping 1、新增 4、搜索 9（八场景加清理复查）、列表 6、单条 GET 8、DELETE 4；所有 HTTP 状态均为 200。四次新增 `status=SUCCEEDED`，未重试。各场景请求时间见上表；八次 A 组中位数 **14.44 ms**、B 组 **1443.30 ms**，逐场景 B−A 的中位数 **1428.09 ms**，范围 **1369.51～1628.74 ms**。这是单次交替执行下的本地端到端观察，包含网络和调度，不能当作服务端延迟保证。测试进程临时使用 10 秒 HTTPX 阶段超时，未改应用默认值。

四次新增 HTTP 分别为 **1982.69、1881.53、1704.06、1732.28 ms**；四次 DELETE 为 **1524.32、1669.53、1621.28、1617.54 ms**。响应中未获得可确认的模型 Token 或费用，未读取计费控制台；**实际费用、Token 与模型用量均未知**，不按零计算。没有发生真实超时、限流或未知写入，也没有主动制造故障或并发压力。
