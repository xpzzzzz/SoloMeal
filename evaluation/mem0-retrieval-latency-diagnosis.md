# Mem0 检索噪声与延迟诊断

> 公开副本：合成记录 UUID 和运行标记已替换为稳定匿名标签；原始证据保存在本机。

2026-10-28。范围为已有真实实验材料与当前代码的只读分析；本报告是本轮唯一新增文件。本轮没有调用 Mem0、Agent 或付费模型，没有改动应用、配置、依赖、既有实验材料或测试数据，也没有部署、提交或推送。文中“实测”指第五阶段已保存的真实服务实验，而非本轮新调用；“代码”指当前工作区静态分析；“假设”尚未验证。

## 结论和证据边界

1. **`ghost` 的存在是测试设计，不是已证明的数据污染。**[预先固定的协议](mem0-real-ab-protocol.json)明确要求向同一个合成用户写入一个与所有固定菜谱无关的食材偏好。真实实验的八次搜索都返回了它和另外三条记忆。固定且宽泛的查询、`top_k=100`、`threshold=0.0`，以及查询不包含当前候选，是有代码证据支持的噪声产生条件；服务端具体为何为该记录赋分、向量模型是否准确，证据不足。没有必要删除这条测试偏好或直接调低返回数量。
2. **候选级评分已有实际字段匹配，但远端检索前没有当前菜谱相关性筛选。**`score_memories()` 对食材和做法做精确匹配，对时间比较估算分钟数；在本次八场景的 25 条 B 组候选观测中，没有任何 `ghost` 理由。S4、S5 两组完整排序及分数相同；这不证明其他数据或其他请求中绝不会受无关记录影响。
3. **额外时间主要落在一次远端搜索调用包围的时间区间，但无法拆出 Mem0 服务端处理时间。**八次 B 组请求各记录一次真实搜索，搜索包装计时中位数 1421.15 ms；此包装包含实验写盘、建 HTTPX 客户端、网络、服务端、收包和 JSON 解析。没有 DNS、连接、TLS、服务端计算或单独写盘分解。A/B 中位数分别 14.44/1443.30 ms，逐对差中位数 1428.09 ms，样本量仅八对。
4. **优先保留现有用户隔离和 ±6 评分，先补隐私安全的分段观测，再验证连接复用及无需推荐时跳过检索。**本轮不实施优化。候选相关性过滤可减少本地无用数据，但仅在收包后过滤不能减少这一次远端查询的耗时或返回数量。跨请求缓存不是第一步，失效正确性尚需设计。

## 一、实际调用链

以下是代码静态路径，实际实验只走推荐 API：

1. [推荐路由](../backend/app/api/planning.py)通过 `get_identity` 获得当前认证用户，调用 `read_memories(db, current[0].id)`，再将结果传入 `recommend`。Provider 从应用状态注入数据库 session；目标用户不是客户端可选参数。用户关闭个性化或 Provider 不可用时返回空记忆。
2. [首页 `recommendations()`](../backend/app/services/home.py)同样调用一次 `read_memories`；首页未选推荐区块时不会运行它，单区块重试是另一个 HTTP 请求。[Agent `advance`/`recommend_meal`](../backend/app/services/agent.py)在处理该工具调用时读取一次，然后传给 planner；其他工具不会因此自动读取。方案预览路径调用 `recommend` 时没有传记忆。本实验并未测量首页或 Agent 端到端延迟，不能据此认定这些入口在同一请求中重复搜索。
3. [MemoryProvider.get_preferences](../backend/app/services/memory.py)向 `/v3/memories/search/` 发送固定查询 `饮食偏好 食材 烹饪方式 时间 ingredient cooking_method time`，并以服务端派生的 `solomeal:<用户标识>` 作为 `filters.user_id`，`top_k=100`、`threshold=0.0`。它不接收请求文本、菜谱、可行候选或本次约束；保留服务端 results 的顺序，不按返回 score 再过滤或排序。
4. Provider 检查结果封套和最多 100 条上限；`_scoped_result` 核验每条的用户归属。缺 `user_id` 时逐条串行单条 GET 校验，在请求间检查剩余预算；归属不符或无法验证时整批退回空。`_decode` 检查 UUID、`memory` 内 JSON 的 `solomeal.preference.v1` schema、类别和字段，转换为 `MemoryPreference`。它校验的是内容中的 schema，不能据此声称原始响应 metadata 已验证。
5. [planning.read_memories](../backend/app/services/planning.py)检查 Provider 返回类型和条目；[filter_suppressed](../backend/app/services/memory_operations.py)按该用户的 `operations` 状态抑制待处理、未知及已退役语义，避免旧快照直接参与评分。Provider 错误和不合契约数据回退空记忆。
6. `recommend()` 在既有硬过滤与原始个性化评分后，才对每个可行候选调用 [score_memories](../backend/app/services/personalization.py)，把记忆分叠加到原始分，再排序。时间、厨具、忌口和已知超预算的菜先排除；预算未知保持现有业务语义。相关理由由 [recommendation_response.render](../backend/app/services/recommendation_response.py)等展示。记忆不创建硬限制；显式收藏或喜欢/不喜欢反馈的候选跳过记忆分；相同对象相反方向忽略、重复记录不叠加，记忆总分仍限于 ±6。

注意时序：当前 **远端读取在硬过滤之前**，只是**加分发生在过滤之后**；因此即便所有候选都不合条件，也可能产生一次远端查询。

## 二、`ghost` 召回分析

### 实验实际记录

- [真实 A/B 报告](mem0-real-ab-report.md)、[逐次证据](mem0-real-ab-evidence.json)与协议表明：四条记录均由合成用户确认并真实写入；无关偏好为 `ingredient`、正向，目标使用带运行标识的 `ghost`。其合成记录 ID 为 `synthetic-id-7`；清理阶段该 ID 删除成功，列表和搜索随后为空。
- 八次搜索均为 HTTP 200、原始封套记录 `result_count=4`；各次适配后的四个 ID 均唯一，顺序均为负向炖煮、正向食材、20 分钟、`ghost`。五个预定义有相关偏好的场景，目标记忆均被返回；`ghost` 也在八次全部返回。连续结果不能视为八个独立用户或不同查询的检索精度样本。
- 实验运行器 RealProvider（运行器保存在本机）在真实 HTTP 后调用父类 `get_preferences()` 并记录转换结果，没有在搜索阶段用 Fake 或手写记忆补充。结合新增 ID、实际单次搜索和适配结果，可以**高置信推断**该 ID 来自远端返回，而非本地缓存或夹具注入。相同顺序只是所见服务端顺序；原始结果及 score 没有保存，无法核算排序分数或证明每次服务端内部排序机制。
- 逐次证据只保留转换后的 `id/category/target/polarity`、顶层响应键与条目数；**没有保存原始条目的 `user_id`、metadata 或 score**。新增代码发送固定 source/schema metadata；归属校验代码、八次各仅一次 HTTP 的事实，支持推断本次各行均通过直接归属校验（缺失归属会触发额外 GET 或整批失败），但不能从脱敏证据独立逐字段核验原始 owner/metadata。其他用户的数据不在本次证据中；此前隔离冒烟范围见 [冒烟报告](mem0-live-smoke-report.md)。
- 搜索不分页，单次最多 100 条；管理列表的 `count/next` 和最多五页属于另一条链路。八次观测均无重复 ID，不能外推其他搜索绝不会重复。大于 100、结果封套异常或归属失败时搜索保守返回空，而不是获取后续页。

### 为什么没有提前排除，造成什么问题

固定查询只表达通用偏好类别，没有当前场景信息；四条结构化记忆均属于同一用户，`ghost` 的类别本身仍合法。宽泛查询及 `threshold=0.0` 为它返回创造了条件，但没有服务端 score 或索引诊断，不能断言究竟由何种匹配规则、向量距离或阈值导致。四条记忆远少于 100，因此这组数据也不能用来证明将 `top_k` 降低不会丢失重要偏好。

**评分前是否有真正相关性校验？** Provider 与 `read_memories` 校验的是类型、schema、归属和本地抑制状态，并不对当前候选做相关性筛选；但 `score_memories` 在给每个候选计分之前，确实执行基于候选现有结构化字段的匹配。这是确定性的业务匹配，不是对查询语义或用户意图的完整理解。此次 `ghost` 与任何候选食材不相等，因而未生成得分或理由。

实际问题是：八次真实搜索都返回了额外记录，32 条返回观测中至少八条是协议定义的 `ghost` 无关观测，检索相关性无法直接由 5/5 召回率代表；结果需要传输、解析和逐候选检查。**没有测得**这条记录单独造成多少延迟、费用或 CPU。更大的用户记忆集合中，无关项可能占用有限的 100 条返回名额，造成相关项截断；这是风险，不是本实验中已观测到的漏召回。它在另一组菜谱中可能是有效偏好，不能永久排除。

## 三、延迟与请求数拆解

运行器（保存在本机）按协议顺序交错发送 A/B；每个 B 请求记录 1 次 Mem0 HTTP、每个 A 请求 0 次。按执行顺序把 `paired_scenarios` 中的八次 search 与八个 B 场景对应；证据没有每条 HTTP 的场景关联 ID，此映射依赖顺序及每组调用数。

| 场景 | A 推荐 ms | B 推荐 ms | B−A ms | 搜索包装 ms | B−搜索包装 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| S1 | 15.84 | 1437.84 | 1422.00 | 1413.17 | 24.67 |
| S2 | 14.57 | 1462.85 | 1448.28 | 1443.80 | 19.05 |
| S3 | 14.30 | 1573.99 | 1559.69 | 1535.63 | 38.36 |
| S4 | 13.11 | 1641.85 | 1628.74 | 1621.39 | 20.46 |
| S5 | 13.24 | 1382.75 | 1369.51 | 1362.94 | 19.81 |
| S6 | 17.86 | 1399.73 | 1381.87 | 1382.61 | 17.12 |
| S7 | 14.58 | 1448.75 | 1434.17 | 1429.12 | 19.63 |
| S8 | 14.24 | 1431.40 | 1417.16 | 1407.01 | 24.39 |
| 中位数 | 14.44 | 1443.30 | 1428.09 | 1421.15 | 20.14 |

这里的搜索包装计时起点在运行器 `save()` **之前**，终点在响应 JSON 解析和客户端关闭之后；包括一次证据文件写盘。结束时另有一次 `save()`、`get_preferences` 记录转换结果时还有 `save()`，也计入 B 端到端而不计入包装。`B−搜索包装` 只是两个嵌套计时的差，并非精确的业务计算耗时；A/B 都是本机 TestClient 和隔离 SQLite，运行器诊断 I/O 也可能影响比较。各列中位数不能直接相减作为逐对差的中位数。上述证据支持主要等待位于包装区间，**不支持**把 1421.15 ms 断言为纯 HTTP 往返、Mem0 服务器处理或 TLS 耗时。

全实验的 32 次远端 HTTP = ping 1 + 新增 4 + 搜索 9（八场景和一次清理复查）+ 管理列表 6 + 单条 GET 8 + 删除 4。**不是每个推荐请求有 32 次 HTTP**。本次八个推荐请求各只有一次搜索，没有实测的追加 GET 或管理列表；一般代码中若搜索行缺 `user_id`，会依次增加归属 GET，但本次未观察到。管理分页、详情和更新删除的 GET 出现在其他管理链路，不应归因于普通推荐。候选评分会逐候选遍历记忆，但没有记录独立转换或评分耗时。

当前 `MemoryProvider._request` 每次新建并关闭 `httpx.Client`，即使应用 Provider 实例复用，连接池也不会在这些调用之间由该实例复用。重复 TCP/TLS 建连可能增加时间，但握手占比未知。HTTPX 文档确认长生命周期 Client 可以连接池复用，实际受服务端及连接寿命影响：[HTTPX Clients](https://www.python-httpx.org/advanced/clients/)。

当前默认 `mem0_timeout_seconds=2`；第五阶段测试进程设置 10 秒。HTTPX 的 connect、read、write、pool 是阶段/等待超时，read/write 还以数据块等待为单位，不是整个推荐或整次 HTTP 的墙钟限时；参见 [HTTPX Timeouts](https://www.python-httpx.org/advanced/timeouts/)。Provider 的 monotonic deadline 在附加归属 GET 前检查剩余时间，但首个 search 不受严格总截止时间中断；后续单次 HTTP 的各阶段仍非严格总时限，数据库和评分也不在该预算内。不能根据这八次 10 秒设置下的无超时结果，断言默认 2 秒在生产环境稳定。未知写入仍按 `operations` 状态抑制，不能自动重发或解锁。

## 五、修复后复验指标与剩余风险
